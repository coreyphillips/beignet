# Splicing a Taproot Asset channel

Proposed protocol for two Beignet peers, roadmap step 12. A splice spends the current channel output, creates a new one, and can move bitcoin, asset units, or both. Until the peers agree which funding transaction has locked, either funding output can determine who gets paid. Each peer must already be able to close and recover its share on either outcome.

## Negotiation

Use one channel per interactive transaction. All attempts spend the same old funding outpoint. A child splice waits for matching locks. Both peers must have negotiated splicing, support the channel's Taproot and HTLC signing modes, and explicitly opt in to a separate, versioned asset interactive-funding feature. The host advertises the corresponding auxiliary provider surface only when it can construct, verify, persist and resolve these transactions. Ordinary channels use their ordinary protocol. A peer missing a requirement declines before construction. The feature number and byte encodings need wire vectors before implementation.

The engine handles the Bitcoin transaction, Bitcoin signatures, transport and channel state. The provider verifies asset histories and authorizations, assigns units by issuance, and supplies the leaves, signatures and proof material for each spend. Both peers check the same transaction independently. A provider verdict belongs to a particular channel, candidate and output. The engine can compare summed units. Only the provider can verify the allocation by asset ID. See [Asset IDs and balances](EXTENSIONS.md#asset-ids-and-balances).

## From proposal to a spendable splice

1. **Agree on the move.** Use the BOLT 2 quiescence handshake and finish outstanding commitment rounds. Record the current cross-signed state and its unresolved HTLCs. In `splice_init` and `splice_ack`, bind the chain, channel, old funding outpoint, both fresh funding keys, attempt ID, signed bitcoin and per-ID contributions of each side, withdrawal scripts and recipients, fee responsibility and positive lock depth. The provider verifies group membership for each issuance. A bitcoin-only splice still moves the complete asset commitment. Check both peers' deadlines before spending time on proofs.
2. **Agree on the layout before computing output scripts.** On the negotiated extension, both peers propose their interactive serial IDs, prevouts, sequences, output roles, amounts, recipients and order, including bitcoin change. The initiator supplies the old shared outpoint and one new channel output. Each contributor supplies script keys, issuance IDs, authenticated input histories and virtual input data. Each output descriptor names its asset script key, Bitcoin internal key, amounts and tree data. Stage large proof files in bounded chunks identified by attempt, object digest and offset. Check declared sizes, hashes and local limits on total bytes, chunks, attempts and time. Both peers acknowledge a canonical digest of these terms, the serial-to-vout map and unsigned virtual transfers before either signs them.
3. **Authorize the assets, then freeze the Bitcoin transaction.** Each peer first verifies the unsigned transfers and the parties' authority to spend their named inputs. Bind the old virtual channel key to the retained jointly controlled funding asset, and the new one to the agreed joint keys. Exchange and verify all required virtual spend signatures, including both shares for a joint spend. Use the agreed output indexes for split commitments. Build the final asset roots from the correctly encoded leaves for each asset version, including witnesses where its encoding requires them. Derive the final Bitcoin scripts from those roots and the agreed keys. A change in layout, recipient or terms starts a fresh attempt with fresh authorization.

   Send the actual BOLT interactive inputs and outputs using the agreed serial IDs. Removal, substitution or any discrepancy with the authorized layout invalidates the attempt. Two consecutive `tx_complete` messages freeze the ordered unsigned Bitcoin transaction. Both peers compare its txid, complete signed virtual transfers, finalized output scripts and attached proof data against a second, final manifest digest. The first digest excludes signatures that have yet to be generated. Neither digest substitutes for verifying the underlying data.

   Each peer checks prevouts against its chain view, input histories back to issuance and all completed spend authorizations. Verify the retained old funding root and its opening. For every added Taproot prevout, including a fee input labeled bitcoin-only, require a complete verifiable opening of the internal key and script tree that accounts for any asset commitment, or decline it. Carry unrelated passive assets unchanged to owner-authorized outputs, outside channel balances, or decline the input. Recreate every output commitment, script, value and index. Check inclusion, exclusions from other applicable Taproot outputs and any split root and additional input proofs. Check consent to every debit, Bitcoin fees, reserves, dust and the carrier needed for each asset-bearing spend. Each ID must satisfy

   `old funding + external asset inputs = new funding + withdrawals + change`.

   Apply this equality per issuance, then check the approved debit or credit of each peer. A withdrawal can consume only its owner's free balance. For example, withdrawing 20 units of A from a funding output with 60 A and 40 B leaves 40 A and 40 B in the new output. A different issuance of the same group cannot cover the 20 A. The old output still backs 60 A and 40 B if the splice never confirms.

4. **Secure both exits before funding signatures.** Each peer builds both commitment views for the candidate at the current commitment number and feerate. Exchange candidate commitment signatures, including the Bitcoin and asset authorizations needed for each applicable second-level HTLC spend. Verify the peer's signatures and the provider data against the exact local transactions. Each peer persists the signed funding asset transfer, a fully enforceable local exit, the matching remote view and the proof templates it needs to recover its own outputs without another response. The initial candidate commitment has no `revoke_and_ack`. The current funding commitment remains usable.
5. **Sign and broadcast.** Only after its own exit and proof data are durable may a peer release a Bitcoin funding signature. Use the ordinary Taproot splice signing protocol from step 13, with the correct asset-root tweak for each funding outpoint. Funding signatures commit to all inputs and outputs of this candidate. Bind each MuSig2 session to the keys, tweak, message, signing purpose, candidate, commitment direction and state as applicable. Allocate fresh signing and verification nonces for distinct sessions, even at the same state number. Atomically consume a secret nonce and store the exact outbound signature before sending. A retry replays the stored bytes. After the ordered `tx_signatures` exchange, publish and watch the candidate. At this stage the proofs describe a possible transfer. Only a block on the accepted chain can supply the anchor inclusion evidence for a confirmed receipt.

Before exposing a Bitcoin funding witness, peers can discard an attempt once both establish that it cannot publish. A funding signature already sent, or uncertainty after a crash about its delivery, makes the candidate potentially publishable. Keep its commitments, proof data, input reservations and watches. A timeout or `tx_abort` cannot take that signature back. Before resuming updates, the asset extension requires an authenticated acknowledgement from each peer of the identical ordered live outpoints and completed signing phases. During a gap, block updates and revocations until exact replay succeeds or a timely chain exit is needed. Disconnection ends BOLT quiescence but preserves this signing restriction.

## While several funding outputs are live

Keep a local and a remote commitment for the current funding outpoint and for each potentially publishable splice. At a common logical state, the old commitments use the old capacity, asset inventory and free balances. Each candidate uses its proposed capacity and the approved per-peer deltas for that candidate. All views carry the same unresolved obligations. The balance equation for each issuance in each view is the sum of the two free balances and the units in unresolved HTLCs. Bitcoin fees and carriers have their own accounting.

| Event | Rule across the live funding outputs |
| --- | --- |
| An HTLC was already committed when the splice began | Carry its direction and ID, payment hash, CLTV, bitcoin amount and exact issuance allocation into both candidate commitments. A plain HTLC carries zero asset units. Derive output indexes, leaves and signatures separately for each transaction and side, including trim rules for plain HTLCs. Require each asset HTLC to have its enforceable output and second-level spend in every view. |
| An add or fee update arrives after funding signatures | Resume updates within the intersection of all live views. An identical per-ID allocation must be spendable from the sender's free balance in each, with sufficient bitcoin, fees, reserves, carrier and wire space. Newly spliced-in units are unavailable until lock. Reserve spliced-out units immediately. Never sum the capacities of alternative outcomes. |
| A fulfil or failure arrives | Record the decision once by channel, direction and HTLC ID. Persist a received preimage or a decision to reveal one before sending it. Apply removal to every live view. Release or transfer the units, and propagate a failure, only at the normal irrevocable removal boundary across the whole set. A reconnect or a different winning candidate cannot pay twice. |
| An HTLC approaches its claim deadline | Preserve absolute expiry throughout construction and RBF. With pending HTLCs, disconnect after 60 seconds of quiescence, or earlier at the claim margin. Proof chunks and retries do not extend the deadline. After an unsigned attempt, reconcile and resume on the old state. Once a candidate may publish, use a valid unilateral close and the matching second-level claim in time if the update cannot complete. Never wait for a proof exchange, peer lock, or replacement past the claim margin. |

For each update round send one BOLT 2 `start_batch` containing a `commitment_signed` for the current funding and each signed pending candidate, tagged by funding txid. Verify the exact member set and each Bitcoin, HTLC and asset signature. Persist the complete round before returning one revocation for the prior state. A partial batch advances no view. Reestablish and replay the exact durable batch or revocation after interruption. Store commitment, revocation, HTLC and sweep data by funding outpoint, side and state number, with direction and ID for the HTLC. The same height or output index in another view does not identify the spend.

Check the maximum encoded size of **each** tagged member before accepting a splice, in both directions, at the negotiated HTLC counts and worst allowed provider signature widths. Include every negotiated TLV and both directions' untrimmed HTLCs. For example, the grouped fixture with a 65,517-byte payload would need 34 more bytes for the funding txid. Its 65,551 bytes exceed the 65,533-byte payload limit. This profile declines a channel whose existing bounds cannot guarantee a fit, even if it currently has few HTLCs. Admission must also respect the BOLT batch limit and the proof and storage limits for all alternatives together.

## Replacement, lock and recovery

Only the quiescence initiator can propose negotiated RBF, using `tx_init_rbf` and `tx_ack_rbf` while quiescent, before a lock has been sent and without zero-conf. This profile permits a fee bump funded by the bumping peer's external bitcoin inputs or bitcoin change. Preserve the shared input, channel contributions, asset inputs, allocations, withdrawal terms and recipients. Check the new feerate, absolute fee and relay rules independently. Rebuild serial mappings, anchor output indexes, proof templates, both commitment views and signatures from the new transaction against the **latest** cross-signed state. Reapply the same input-opening and output-exclusion requirements to new fee inputs or change. Use fresh nonce sessions. Repeat the same proof and exit checks before funding signatures. Decline a replacement outside these terms, above resource limits or when a candidate has already been seen in a block. The existing signed attempts stay live.

A peer can publish an earlier signed candidate at any time. Mempool replacement, eviction or a conflict with an external input does not select a winner. Watch every candidate and the shared funding outpoint. Even a confirmed external conflict can be reorged. Keep every signed candidate in every update batch until matching locks or unilateral close. If the set cannot be maintained, freeze updates and revocations and resolve on chain.

* **Before lock.** If the shared output is still unspent on chain, the latest unrevoked old commitment is an available exit. Once a candidate is mined, close against that candidate as soon as required, even below lock depth. Either peer's commitment or a revoked commitment must be recognized by its actual prevout and txid. Select the matching proofs, HTLC claim or revocation remedy. A reorg retracts provisional receipts and re-drives the close against the surviving outpoint.
* **At lock.** Each peer verifies the candidate, chain inclusion, required depth and asset proofs before sending its `splice_locked`. Adopt only after both locks name the same txid on the local accepted chain. Divergent locks keep resolution data live. Apply the agreed deltas once, import the winner's confirmed proofs and release the losing input reservations when safe. Serialize adoption with any in-flight commitment round so a crossing batch can finish under the BOLT lock rules. Retain historical commitments and remedies through the reorg and dispute windows. A deeper reorg after adoption requires chain resolution and reconciliation before resuming updates.
* **On restart.** Persist the manifests, signed transactions and proof material per attempt, nonce consumption, outbound messages, all funding watches, local and remote locks and HTLC decisions before the messages that depend on them. Reconcile `next_funding`, lock txids and commitment counters on reestablish. Also compare the full ordered set of outpoints and signing phases under the extension. Replay missing messages and reconcile the set before any new update or revocation. Missing candidate data or a stale backup freezes new signatures and revocations. Use chain observation and the recovery procedure for that backup before choosing an exit. An old snapshot alone cannot establish that its commitment is still unrevoked.

## Checks before enabling the feature

Step 13 establishes ordinary Taproot interactive opening and splicing. Step 14 uses the proof and exit sequence for an opening with two contributors, where there is no old funding outpoint. Step 15 exercises units in, units out and a bitcoin-only splice with two peers. Step 16 covers chain resolution and recovery before release.

Acceptance cases include both peers contributing, wrong per-ID totals with a correct group total, a removed or reordered output, missing proof data, a tag that exceeds the message limit, mixed plain and asset HTLCs carried and resolved during the window, and a disconnect on either side of each signature and revocation. Drop the last replacement funding-signature message and mine the original. Mine the replacement in a separate run. Exercise a unilateral close and a revoked commitment on each possible funding output, a reorg below lock depth, and restoration from before and after the splice. In each case compare the actual outpoints, per-ID receipts, HTLC outcomes and spendable balances.

The underlying protocols are described in [BOLT 2, channel splicing](https://github.com/lightning/bolts/blob/master/02-peer-protocol.md#channel-splicing), [BIP 327, MuSig2](https://github.com/bitcoin/bips/blob/master/bip-0327.mediawiki), the [Taproot Assets leaf encoding](https://github.com/lightninglabs/taproot-assets/blob/main/asset/asset.go) and the [Taproot Assets proof format](https://github.com/lightninglabs/taproot-assets/blob/main/proof/proof.go). The engine's distinction between observing a splice and locking it is described in [Depth-locked splices](SPLICE-LOCK-DEPTH.md).
