# Host extensions

A host extension is code the operator names at start that runs inside the daemon, beside the wallet it serves. It gets the on-chain wallet, its own rows in the node's database, a logger and an event emitter. The daemon serves its routes under `/x/<id>` and relays its events on `GET /events`.

The contract exists for features that need the wallet's keys and coins in the same process, and that do not belong in the engine: a second protocol built on the wallet's UTXOs, for instance. It is not a plugin market. An extension is trusted exactly as much as the engine is, because it runs with the same keys.

Contract version: `beignet-extension-api/1` (`EXTENSION_API`, with `EXTENSION_API_VERSION = 1`). The number moves only on a breaking change.

## Naming an extension

Only the process that starts the daemon can name one:

```bash
beignet start --extension /opt/app/assets-host.js          # repeatable
BEIGNET_EXTENSIONS=/opt/app/a.js,/opt/app/b.js beignet start
```

`config.json` cannot, and no route can. `POST /config` and every other API call reach `config.json`, so a setting there would let an API caller load code into the process that holds the seed.

The path must be absolute. On POSIX the file (after symlinks are resolved) and its directory must belong to the user running the daemon or to root, and be writable by no one else. The daemon refuses to start on a path that fails these checks, on an `--extension` with no path after it, on a module that does not load, and on a description it cannot serve. It says which, as `START_FAILED`, and nothing is left running.

A library host passes the same objects to `BeignetNode.create({ extensions })` or `startDaemon({ extensions })`.

## The module

The file is a CommonJS module that exports `beignetExtension`: the extension, or a function returning it (or a promise for it).

```js
const { ExtensionError } = require('beignet/node');

exports.beignetExtension = ({ network, env, engineVersion, api }) => ({
	id: 'notes',
	version: '1.0.0',
	api: 1,
	events: ['saved'],
	routes: [
		{ method: 'GET', path: '/list', scopes: ['readonly'], summary: 'List notes' },
		{ method: 'POST', path: '/save', idempotent: true, summary: 'Save a note' }
	],
	attach({ wallet, storage, logger, emit, generation }) {
		return {
			handlers: {
				'GET /list': () => ({ notes: storage.list('note/') }),
				'POST /save': ({ body }) => {
					if (typeof body.text !== 'string') {
						throw new ExtensionError('TEXT_REQUIRED', 'text is required', 400);
					}
					storage.set(`note/${Date.now()}`, body.text);
					emit('saved', { length: body.text.length });
					return { saved: true };
				}
			},
			start() {},
			stop(reason) {},
			status: () => ({ notes: storage.list('note/').length })
		};
	}
});
```

| Field | Rule |
|-------|------|
| `id` | 2 to 32 characters: lowercase letters, digits and hyphens, starting with a letter. It is the route prefix (`/x/<id>`), the event prefix (`<id>:`) and the storage namespace (`x/<id>/`). It may not be the prefix of the node's own events (`channel`, `payment` and so on) |
| `version` | The extension's own version, reported by `GET /extensions` |
| `api` | The contract version it was built for. Anything but `1` refuses the start |
| `routes` | Static. `method` is `GET`, `POST` or `DELETE`; `path` is lowercase segments such as `/send/prepare`, with no parameters (those go in the query or the body) |
| `events` | The names it may emit: lowercase letters, digits and hyphens |
| `attach(context)` | Returns the attachment, or a promise for it |

The factory's argument carries `network`, the daemon's `env`, the engine's package version as `engineVersion`, and `api`. An extension that needs a particular engine release checks `engineVersion` itself and throws.

## Lifecycle

1. **Start refused or not.** Descriptions are checked before the instance lock and the database are taken.
2. **`attach(context)`** runs once the on-chain wallet exists and before the Lightning node is created, so nothing has spent from the wallet yet. It has 30 seconds. `context.generation` is 1.
3. **`bind(node)`**, for an attachment that has one, runs as soon as the Lightning node is constructed: before it restores its stored channels, so before any hook of `auxiliaryChannels` can be called, and before any `start()` ([Asset channels](#asset-channels)).
4. **`start()`** runs in the background once the node is built. The daemon does not wait for it, so a slow extension never delays the node, and the extensions are started together, so one never delays another. It has no time limit: an extension stays `attached` until its `start()` returns, and is `ready` after. Routes are served from `attach` on: an extension that is not ready yet says so in its own answers.
5. **`stop('shutdown')`** runs when the daemon stops, before the node and the wallet do. On a graceful stop the storage still takes writes while it runs. The hooks of all extensions run together under one limit: 5 seconds, or half the time the shutdown was given when that is less. That wait is part of the shutdown's time, not added to it, so an extension that hangs shortens the node's wait for payments in flight and never delays the wallet's stop or the database's close. A node destroyed without a graceful stop (`BeignetNode.destroy()`, the fallback when the graceful one fails) fences the storage first and does not wait for the hook.

An in-process rebuild replaces the node and the database under a running daemon (a capsule restore, [RECOVERY-PROTOCOL.md](RECOVERY-PROTOCOL.md)). Then:

1. The extension's rows are copied into the database being installed, with the rest of the daemon's own state. From that copy on, `set` and `delete` through the running generation's storage throw: a write the installed database would not have is refused, not acknowledged and lost. Should the install give up before it replaces the database, they work again.
2. The storage view and the emitter of the running generation are fenced, synchronously, in the same turn as that copy. From that point every storage call through the old context throws `The database connection is not open`, and `emit` does nothing. Nothing the old generation does can reach the installed database.
3. `stop('rebuild')` runs, bounded. It must not expect to write.
4. `attach` runs again on the new wallet and database, with `generation` one higher, once the previous `stop` has returned or timed out. Then `bind` with the new node, then `start`.

Keep nothing from one generation for the next. Everything an extension needs after a rebuild is in its rows.

A daemon holding for a guardian restore has no node, so no extension is attached until the restore completes.

## What a failure does

| What breaks | What happens |
|-------------|--------------|
| The path, the module, or the description | The daemon does not start |
| `attach()` throws or does not answer in 30 seconds | The extension is `failed`. The node is built without it and the wallet runs. An attachment that arrives after the 30 seconds is stopped with `stop('shutdown')` |
| `attach()` returns handlers that do not match the routes | The extension is `failed`, and the `stop('shutdown')` of what it returned runs, so whatever `attach()` opened can be closed |
| The attachment's `auxiliaryChannels`, `fixedOutputFees` or `bind` is malformed | The extension is `failed` and its `stop('shutdown')` runs. The node is built without its provider, which refuses the start when asset channels are stored (`ASSET_PROVIDER_REQUIRED`) |
| The wallet refuses the fee policy | The extension stays attached and the node is built with its provider, so a wallet that holds asset channels starts and runs them. It has no fee coin pool: `GET /extensions` reports `fixedOutputFees: { available: false, error: { code: "FEE_POLICY_REFUSED", remedy: "operator", message } }` for the extension, `node.getFixedOutputFeeStatus()` answers `{ available: false, error }`, the node opens and accepts no asset channel, and whatever needs a fee coin fails with that `FixedOutputFeeError`. Supply a policy the wallet takes and restart |
| The attachment supplies `auxiliaryChannels` without `fixedOutputFees` | The node is built with the provider and a wallet that keeps no fee coin pool. It does not offer fixed HTLC outputs (feature bit 451 is not in its init), so `getAuxiliaryHtlcMode(peer)` and an opening are refused with `New asset channels require fixed HTLC outputs or explicit peer compatibility` unless the provider's `allowLegacyHtlcSignatures` allows the peer, on both sides. `GET /extensions` reports `fixedOutputFees: { available: false, supplied: false }` for the extension, and `node.getFixedOutputFeeStatus()` answers `undefined`. Supply a fee policy and restart |
| Two extensions both supply `auxiliaryChannels` | The start is refused: `ASSET_PROVIDER_CONFLICT` |
| `bind()` throws | The extension is `failed` and its `stop('shutdown')` runs. If the node is being built with its provider, nothing is restored and the start is refused: `ASSET_PROVIDER_FAILED` |
| `start()` throws | It is `failed` and its routes close at once; then its `stop('shutdown')` runs. An extension whose provider the node holds is the exception: it is not stopped and its storage stays open, and its `stop` runs when the node stops or is rebuilt |
| `start()` never returns | It stays `attached`. The other extensions start, and the node runs |
| `stop()` throws or hangs | Logged; the node moves on after 5 seconds |
| `status()` throws, or returns something that is not JSON | Logged; `GET /extensions` reports the extension without `status` |
| A handler throws an `ExtensionError` | The caller gets that refusal (below) |
| A handler throws anything else, a `BeignetError` included | Logged with its stack; the caller gets a generic `500 INTERNAL_ERROR`. The engine's codes are not an extension's to answer with |

A failed or stopped extension's routes answer `503 EXTENSION_UNAVAILABLE` with the reason, not `404`: the route exists, and a restart may bring it back. `GET /extensions` reports each extension's `state` (`pending`, `attached`, `ready`, `failed`, `stopped`), the `error` of a failed one, whatever its `status()` returns, and `fixedOutputFees` only when the wallet refused the fee policy it supplied.

## Routes

A route is served at `/x/<id><path>` (and under `/v1`), through the same request path as the daemon's own:

- **Authentication and scopes.** `scopes` lists the non-admin scopes that may call the route: `readonly`, `invoice`, or both. Omitted means admin only. A path under `/x/` that no extension declared is admin only and answers `404`.
- **Rate limiting, CORS, the browser guards** apply unchanged.
- **Holds.** While the daemon holds for a restore or a restart, extension routes answer `503 NODE_RESTORE_PENDING` or `NODE_RESTART_REQUIRED` like every other route.
- **Body.** JSON, at most 1 MiB, or the route's `maxBodyBytes` (up to 32 MiB).
- **Answer.** Whatever the handler returns is wrapped as `{ "ok": true, "result": ... }`; a handler that returns nothing answers `null`.
- **Idempotency.** A `POST` declared `idempotent` honours `X-Idempotency-Key` the way the daemon's own routes do: a repeat with the same key and body gets the first answer, a concurrent repeat waits for it, and the same key with another body answers `409 IDEMPOTENCY_CONFLICT`. That cache is in memory. The handler also receives the key as `idempotencyKey`, and an extension that moves funds must record it in its own rows, so that a retry after a restart is recognised too. Any other `POST` that carries the header answers `400` and runs nothing.
- **OpenAPI.** The daemon's `GET /openapi.json` lists the routes with their `summary`, `requestSchema`, `responseSchema` and accepted scopes. `getOpenApiSpec()` describes the engine alone.

### Refusals

```js
throw new ExtensionError('INSUFFICIENT_BALANCE', 'Not enough to send', 409, {
	needed: '1200',
	held: '500'
});
```

answers with that status and

```json
{
	"ok": false,
	"error": {
		"code": "EXTENSION_ERROR",
		"message": "Not enough to send",
		"extension": {
			"id": "notes",
			"code": "INSUFFICIENT_BALANCE",
			"details": { "needed": "1200", "held": "500" }
		}
	}
}
```

`error.code` is always `EXTENSION_ERROR`, so the engine's own codes stay a closed set, and `error.extension.code` is the extension's (capitals, digits and underscores). The status is one of 400, 403, 404, 409, 410, 413, 422, 429, 500, 502, 503 and 504; anything else becomes 400.

The daemon reads the refusal by shape, not by class: any `Error` with a string `extensionCode`, and optionally `status` and `details`, is one. An extension that cannot import `ExtensionError` from the engine it runs in can throw its own.

## Storage

`context.storage` is the extension's rows in the node's SQLite database:

```ts
interface IExtensionStorage {
	get(key: string): string | null;
	set(key: string, value: string): void;
	delete(key: string): void;
	list(prefix: string): Array<{ key: string; value: string }>; // '' lists all
	transaction<T>(fn: () => T): T;
}
```

- Rows live in the `metadata` table under `x/<id>/`. Keys are given without that prefix, and one extension cannot read another's.
- Values are strings, encrypted at rest with the rest of the table when storage encryption is on (the default).
- Every call is synchronous and durable when it returns (the database runs with `synchronous = FULL`).
- `transaction(fn)` is atomic: a throw undoes every write `fn` made. `fn` must be synchronous. A promise it returns is not waited for, and writes made after an `await` are outside the transaction. Transactions do not nest: a call made while one is open throws before its `fn` runs, because an inner one could not be undone on its own.
- The rows are part of the database: `beignet backup` copies them, and an in-process restore carries them into the installed database (the carry is mandatory, so a restore that cannot copy them does not install).
- They are not in a static channel backup, and the recovery phrase does not recreate them. An extension whose rows are the only record of funds must offer its own export, and say so to its users.

The view needs a backend with `loadMetadataByPrefix` and `deleteMetadata`. SQLite and the in-memory backend have both; on an injected backend without them, `attach` sees storage calls throw.

## Events

`context.emit('saved', data)` reaches subscribers of `GET /events` as `event: notes:saved`, and webhooks registered for `notes:saved` or `*`. `data` must be JSON-safe. A name the extension did not declare is dropped with a warning in the log, and so is anything emitted after `stop`.

## The wallet

`context.wallet` is the engine's `Wallet`, the same instance the node uses. Two rules follow from sharing it:

- **Coins.** Anything the extension must keep out of ordinary coin selection (an output that carries something other than bitcoin) has to be frozen with the wallet's own freeze, which is persisted with the wallet's data. Do it in `attach`, before the node can spend.
- **Fees and broadcasts** go through the wallet's API. The daemon's spending limits (`maxPaymentSats`, `dailySpendLimitSats`) apply to the daemon's own routes, not to what an extension spends through the wallet directly. An extension that spends states its own limits.

The Lightning node is not in the context. An attachment that needs it asks for it with `bind(node)`.

## Asset channels

Three optional members of the attachment reach the Lightning node. They were added to version 1 without a new contract number, because an engine that predates them reads an attachment by the members it knows and ignores the rest: the extension attaches there as before, its `bind` is never called, and the node runs no asset channels. An extension tells the two apart by whether `bind` ran before its `start()`.

```ts
interface IExtensionAttachment {
	// ...handlers, start, stop, status
	auxiliaryChannels?: IAuxiliaryChannelConfig;
	fixedOutputFees?: {
		maxFeeSatoshis: bigint;
		maxTotalFeeSatoshis: bigint;
		maxPreparationFeeSatoshis: bigint;
		feeCoinCount?: number; // 1 to 16, 4 when left out
		preparationFeeRatePerVbyte?: number; // the least a split pays: 1 to 10000, 1 when left out
		walletCallTimeoutMs?: number; // 1 to 600000 ms, 30000 when left out
	};
	bind?(node: LightningNode): void;
}
```

- **`auxiliaryChannels`** is handed to the node as its `auxiliaryChannels`, untouched: the provider that extends the channel state machine and the hooks that tie funding, payments and forwards to the extension's protocol. One extension may supply it. The node holds it for the life of the build, whatever becomes of the extension afterwards: an attachment with no handlers and no `start`, one whose `start()` has not returned, and one whose `start()` threw all leave their provider with the node. So the provider has to answer from the moment the node is bound. When the `start()` of such an extension throws, it is reported `failed` and its routes close, but it is not stopped and its storage is not fenced: the node still calls its provider for the channels that exist, which it may have to defend on chain. Refusing new activity from then on is the extension's own to do. Its `stop` runs when the node stops or is rebuilt. At a graceful shutdown the extension that supplies the provider is the last to stop: its routes close with the others, but its `stop()` runs, and its storage is fenced, only after the node has drained its in-flight HTLCs, because the node calls the provider for every commitment until then.

Asset channels and the recovery mode. A wallet whose recovery mode is a guardian mode (`async-remote` or `quorum`) neither opens nor accepts an asset channel: `openAuxiliaryChannel` throws `AuxiliaryGuardianModeError` (`AUXILIARY_GUARDIAN_MODE`), and an incoming asset opening is refused. A wallet that already holds asset channels does not start in a guardian mode at all: the daemon refuses the boot with `ASSET_GUARDIAN_START_REFUSED` before a guardian is asked anything, before the node is built and before anything is replicated (the engine's own refusal, for a host that builds the node itself, is `AuxiliaryGuardianStartError`, `AUXILIARY_GUARDIAN_START_REFUSED`), and the database is left as it was, so the wallet starts again in `peer-storage` or `off`, where the channels can be closed. The recovery journal carries the node's rows for a channel and nothing of what the extension keeps beside them, and a guardian restore puts those rows on another device. So no guardian journal ever holds an asset channel, a guardian restore is never handed a provider, and a journal from the guardians that does hold one is refused whole as one this build never replicates (`AuxiliaryGuardianRestoreError`, `AUXILIARY_GUARDIAN_RESTORE_REFUSED`; `ASSET_RESTORE_REFUSED` from the daemon). That refusal comes after the takeover, because the driver downloads the journal only once the old writer is fenced, which is why the refusals at the start and at the opening come first. For the same reason a restore from peer storage that holds asset channels is refused, with nothing of it installed, unless the `auxiliaryChannels` the extension supplied has a `canRestore(channels)` that returns `true` for them: `ASSET_RESTORE_REFUSED`, or `ASSET_PROVIDER_REQUIRED` when no attached extension supplies asset channels. Each channel is given with its id, its peer, where it comes from (`journal` or `static-backup`) and, from the journal, its asset funding data. An entry of a static channel backup that is an asset channel is skipped on the same terms. `canRestore` is synchronous, and only a plain `true` is a yes. It is asked before the install opens, outside any storage transaction and with nothing of the restore written yet, for exactly the channels the restore then installs.

A restore may leave its asset channels out. The refusal of a capsule restore lists them: `error.details.assetChannels` is an array of `{ channelId, peerPubkey, capacitySats }`, one for each asset channel the capsule holds, on both `ASSET_RESTORE_REFUSED` and `ASSET_PROVIDER_REQUIRED`. Run again as `POST /recovery/restore-capsule` with `{ "confirm": true, "omitAssetChannels": true }` (CLI `beignet recovery restore-capsule --omit-asset-channels`; `restoreFromCapsules({ omitAssetChannels: true })`), the restore installs everything else and answers with the same list under `omittedAssetChannels`, present only when a channel was left out. Only the boolean `true` asks for it, and anything that is not a boolean is `INVALID_PARAMS`. Every asset channel the capsule holds is then left out, whether or not an extension could have restored it, and no `canRestore` is asked. No row of such a channel is written: not its state, its chain monitor, its stored messages or its HTLC rows. Its key index is kept, so its keys are never derived for another channel, and payments and invoices stay as the wallet's history. At Tier 1, where the capsule's backup is all there is, the backup's asset entries are left out of the recovery and listed the same way, and at Tier 2 a channel left out is not sent through the peer's recovery either. A channel left out is not watched and not closed by this wallet: whatever it held stays where the peer and the capsule have it, and the peer will in time close it on its own. A payment that was in flight on a channel left out is unresolved. Every payment record that is PENDING at the restore, sent or received, and has an HTLC in the stored state of such a channel is marked: `unresolved: { code: 'CHANNEL_OMITTED_AT_RESTORE', channelIds }` on the record (`IPaymentInfo.unresolved`), on its row of `GET /payments` and, for an invoice that is not paid, on its row of `GET /invoices`; the restore lists the marked by payment hash in `unresolvedPayments`. The record stays PENDING, because nothing else is true: the peer still has the channel and may settle or fail the HTLC, and a capsule can be older than the wallet's last word on it, so neither a payment sent nor a payment received can be said to have failed. No clock fails a marked record, `POST /payment/cancel` refuses it with `PAYMENT_UNRESOLVED` (409), no `payment:failed`, `payment:sent`, `payment:received` or `invoice:settled` is sent for it, no bitcoin total counts it as paid, and its hash is not sent for again. A wait on it (`awaitPaymentResolution`) ends at once with `PaymentUnresolvedError`. Nothing of the channel is acted on: no HTLC of it is held, and a settle of a held invoice on it moves nothing. A marked payment leaves the mark only when an HTLC on a channel the wallet does hold settles it. There is no call that settles or fails a marked payment by hand, and none is meant: the wallet cannot know how the HTLC ended while the peer still holds the channel, so an operator's word would put a guess on the record as a fact. The journal installed is the capsule's own and still names the channels, and the wallet does not hand that journal on: the node takes a snapshot of its tables before the first capsule of each run, so the first capsule a restored wallet gives its peers holds no row of a channel left out and carries the marks, and a restore from that capsule is not refused and brings no channel back. Only a host that composes a capsule itself from the restored database before any node ran on it gets one that still names the channels; a restore from that one is refused as the first was and leaves them out again when asked. A wallet set to apply a capsule without asking (`recoveryAutoApply`) runs the same restore with nothing asked of it, so it is refused by the same code, installs nothing and never leaves a channel out by itself. Nobody called, so the refusal is kept where a client reads it: `GET /recovery/status` answers `autoApply.phase: "refused"`, `autoApply.lastReason` beginning with the code, and `autoApply.refusal: { code, assetChannels }` with the list the route would answer, and the `recovery:restore-progress` event of type `capsule:auto-refused`, over SSE and webhooks, carries the same `refusal`. `capsules.candidates` and `capsules.best` of the same answer say the capsule still waits, the apply is not run a second time, and the confirmed call with `omitAssetChannels` restores it; `refusal` is gone from the status once a restore is installed. A refusal that is not about asset channels has no `refusal`. At Tier 1 nothing is refused: an asset entry of the backup is skipped with its reason and the rest is recovered, by the route and by the automatic apply alike, and the entries skipped are listed as a refusal lists them, under `skippedAssetChannels` in the route's answer and under `autoApply.skippedAssetChannels` after an automatic apply. There is no other way in: the CLI command calls the route, and a daemon that starts over a restore whose file swap did not complete finishes that install as it was decided, refused or asked for, and decides nothing again. The engine's own option, for a host that calls `restoreFromRecoveryCapsule` or `restoreBestRecoveryCapsule` itself, is `omitAuxiliaryChannels: true`, with the list in the result's `omittedAuxiliaryChannels` and, on a refusal, read by `refusedAuxiliaryChannels(err)`.

Asset payments and the spending limits. An asset payment leaves through the node the extension was given (`sendPaymentToRoute` with `assetPayment`), not through a route of the daemon, so the daemon sets the node's payment gate (`setAuxiliaryPaymentGate`) on every node that runs asset channels. Each asset payment is admitted there exactly as `POST /payment/send-to-route` admits a route: drain mode, the per-payment limit, the daily limit, and a claim on the daily budget under the payment hash, all on what the route asks its first hop to carry, in sats, and never less than the bitcoin the HTLC carries. A settled payment is charged to the same daily ledger as any Lightning payment. A payment sent in parts, by a host that sets `sendInParts`, is admitted part by part and judged whole: see "The spending limits" under "An asset payment sent in parts". A refusal is thrown from the send as `AuxiliaryPaymentError` with code `ASSET_PAYMENT_REFUSED`, the limit's own code in `reason` (`SPENDING_LIMIT_EXCEEDED` or `SERVICE_DRAINING`) and its sentence in `message`; nothing was recorded, sent or claimed. The gate is the daemon's: an extension that sets another, or removes it, takes its payments out of the wallet's limits. On the same nodes the daemon sets the node's forward gate (`setAuxiliaryForwardGate`): while drain mode is on, a forward with an asset leg is refused before anything of it is offered (`SERVICE_DRAINING` in the log's `gateReason`), so a drain before a stop or a downgrade starts no new one. A drained stop (`POST /stop` with `drain`) also waits, up to its `drainTimeoutMs`, while such a forward is in flight or an end of one waits for its host, so those in flight end first. Drain mode refuses no ordinary forward, as before, and no limit of the daemon counts a forward. An extension that sets another forward gate, or removes it, takes its forwards out of drain mode.

Asset channels, proofs and rebalances. The proof of a payment that asset HTLCs carried (`getPaymentProof`, `GET /payment/proof`) has `auxiliary: true` and `auxiliaryValueSats`, since its `amountSats` and `feeSats` are the bitcoin that carried the asset; the proof of any other payment is what it was. A rebalance never has an asset channel as either of its two channels: the engine refuses it with `AuxiliaryPaymentError` `ASSET_PAYMENT_UNSUPPORTED` naming the channel, and the daemon with `INVALID_PARAMS` before its fee cap is charged. A hold invoice that an asset HTLC pays says so while the HTLC is held and after: the node's `hold:accepted`, `hold:settled` and `hold:cancelled` events and the rows of `listHoldInvoices()` and `listHeldHtlcs()` carry `auxiliary: true` when a part of the set holds units, and so do the daemon's `hold:*` events, over SSE and webhooks, and its `GET /invoices/held` rows. `heldAmountMsat` is unchanged: it is what the node holds for the HTLC, which for an asset HTLC is what the provider valued it at. The row of a cancelled hold, which holds nothing, has no mark, and neither has anything of an ordinary hold. A swap is not funded against a held asset HTLC: the snapshot of the held set that the swap provider reads says a set with an HTLC that holds units is not complete, whatever the provider valued it at, so the swap pays nothing out on the chain and the set is failed back with its invoice like any set that fell short; `getHeldInvoiceSnapshot` itself answers what it did.

Asset channels and the balance. `getBalance()` and `GET /balance` say the bitcoin on this wallet's side of its asset channels apart from every bitcoin figure: `assetChannelClosingSats` for those that are closing (shutting down, negotiating a close, or force closed with the wallet's balance output not yet spent in a block), and `assetChannelSats` for every other one that is not over, whatever its state: still opening; open; waiting for its peer; failed and not yet closed. Every asset channel that is not over is in exactly one of the two. A channel is counted once its funding transaction is out: one this wallet funds from the moment the node has broadcast the transaction and the network took it, one the peer funds from the moment the node has seen it confirmed (`node.isFundingBroadcastOrConfirmed(channelId)` is the engine's answer). Until then it is in neither, because the coins a funding transaction spends are still in `onchain` while the transaction only exists, so an opening given up between `funding_created` and the broadcast is never counted. A funding the host signs and publishes itself (`prevoutScripts`) is counted from its confirmation. After a restart a channel whose funding is still unconfirmed is counted again once the node has handed the retained transaction to the network again, which it does when it starts and on every block. Neither figure is in `lightning` or `total`, and each is present only while the wallet has such a channel, so the answer of a wallet without one has the keys it always had. A closing asset channel is in no figure for bitcoin on its way back to the wallet (`pendingCloseBalanceSats`): its bitcoin stays under the asset outputs the provider closes or sweeps to, and is the host's to show from there.

Asset channels and mainnet readiness. The channel checks of `getMainnetReadiness()` are about sending and receiving bitcoin, so they read ordinary channels only. A wallet whose only channels are asset channels is told so by the four checks whose sentence for a wallet with no channel would not be true of it: `ANCHOR_CHANNELS_PREFERRED` answers `No ordinary Lightning channel yet (anchor will be used by default); asset channels are not counted here`, `SUFFICIENT_CHANNELS` answers `No ordinary Lightning channel yet; asset channels are not counted here`, `HAS_ACTIVE_CHANNEL` answers `No active ordinary Lightning channel: open one to send and receive bitcoin over Lightning; asset channels are not counted here` and `CHANNEL_BALANCE_HEALTH` answers `No active ordinary Lightning channel to assess; asset channels are not counted here`, each with the status it has for a wallet with no channel, so the score is that wallet's too. A wallet without an asset channel is answered what it always was, and so is a wallet that holds an ordinary channel, ready or not, whatever asset channels are beside it.

Asset channels and an older release. An asset channel's row is stored inside an envelope (`{ "assetChannelRow": 1, "channel": { ... } }`) that a release from before asset channels cannot decode; a channel without asset state is stored as the bytes it always was. The published 0.42.0, started over a database that holds an asset channel, skips that row as corrupt, reports it (the storage's `onCorruptRow` callback and `corruptRowCount()`, which the daemon logs as `Skipped corrupted storage row during load`), starts, runs its ordinary channels, and leaves the row and everything else stored for the channel as it was, so a return to a build that knows asset channels has the channel whole. With the recovery journal on it also records `recovery_capsule_rebase_failed` and writes no new frame, because it will not snapshot a database it cannot fully read. While the older release runs, the asset channel is neither run nor watched: nothing answers its peer, enforces an HTLC deadline or punishes a revoked commitment, so a downgrade over an open asset channel is for getting back, not for staying. `tests/lightning/auxiliary-downgrade.test.ts` drives the published 0.42.0 over a database this build wrote; it needs `BEIGNET_RELEASED_0_42_0` to name an installed copy and is skipped without it.
- **`fixedOutputFees`** bounds what the wallet may spend on the fees of an asset channel's transactions whose outputs are fixed, which cannot pay a fee from change. With it the wallet keeps a pool of fee coins. When a transaction needs a fee that no coin of the pool covers, the wallet splits one confirmed ordinary coin into at most `feeCoinCount` equal fee coins, each the size of the fee that was asked for, pays the change back to itself, and the transaction then spends fee coins whole. Only fee coins the pool's own splits made are spent this way: an ordinary coin is never burned whole, however small. From the moment a split is signed its fee coins are left alone by every ordinary coin selection, and once the wallet lists them they are frozen, until a fee action takes one. `maxFeeSatoshis` is the most one fee action may burn across all its replacements, not the size of a fee coin. `maxPreparationFeeSatoshis` is the most one split may pay in its own fee: a split that cannot fit it makes fewer coins, and when not even one coin fits it is refused (`FEE_PREPARATION_FEE_EXCEEDS_CAP`) with nothing recorded. `maxTotalFeeSatoshis` is the most all of them together may ever commit. That last one is a lifetime budget kept in a journal in the node's database: it is charged what each fee action still open can still spend, what a retired one was charged, and the fee of each split. An open action can still spend its cap until it has fee coins; from then on it can spend the fee coins it holds, with any it let go of that an earlier form of its spend may still burn, and never more than its cap. So a spend that is out holds the fee it carries, not its cap, and a raise that takes more fee coins needs room in the budget for the difference: when there is none the raise is refused (`FEE_BUDGET_EXHAUSTED`) and the spend stays out at the fee it has. The budget stays a hard total: what is held and what was spent never pass `maxTotalFeeSatoshis`. A retired action is charged the fee coins that the transaction named at its retirement spent, and the coins that transaction did not spend go back to the pool. One retired with no transaction named is charged its whole cap, because a wallet that still lists a coin does not show it unspent. The three bounds govern new actions and new splits only. A policy lowered below what the journal holds still builds and completes everything recorded, and refuses only new actions (`FEE_BUDGET_EXHAUSTED`, with the figures). Every refusal of the pool is a `FixedOutputFeeError` with a stable `code` and a `remedy`: `wait` (`FEE_PREPARATION_PENDING`, `FEE_PREPARATION_NOT_PUBLISHED`, `FEE_WALLET_TIMEOUT`, `FEE_WALLET_UNAVAILABLE`, `FEE_RESERVATION_REFUSED`), `operator` (`FEE_BUDGET_EXHAUSTED`, `FEE_FUNDS_UNAVAILABLE`, `FEE_ACTION_CAP_EXHAUSTED`, `FEE_PREPARATION_FEE_EXCEEDS_CAP`, `FEE_PREPARATION_SIGNING_FAILED`, and `FEE_POLICY_REFUSED` when the wallet refused the policy itself and there is no pool) or `none` (`FEE_ACTION_RETIRED`, `FEE_INPUT_UNAVAILABLE`). One split that cannot go on holds back no fee action that the coins already in the pool can serve. `walletCallTimeoutMs` (1 through 600000, default 30000) bounds how long the pool waits for any one wallet call, so a call that never answers fails that one selection with `FEE_WALLET_TIMEOUT` and not every later one. The fee journal is not carried by a recovery capsule or a guardian journal: a restore starts the budget afresh, and the freezes the pool left in the wallet are released when the wallet is next built. An extension reads the pool through the node it was bound to: `node.getFixedOutputFeeStatus(forFeeSatoshis?)` answers the budget (`totalSatoshis`, `reservedSatoshis`, `spentSatoshis`, `remainingSatoshis`), the fee coins no action holds (`feeCoins.ready` confirmed, `feeCoins.unconfirmed`), the open `actions` with their ids and caps, the `splits` on their way with their state, the `lastRefusal` a fee selection ended with (`code`, `remedy`, and `at` in milliseconds), and `preparation`: whether a split for a fee coin of `forFeeSatoshis` (the policy's `maxFeeSatoshis` when left out) could be made now, that is, whether the wallet lists a confirmed ordinary coin of at least `neededSatoshis` and the budget has room, so a host can warn a user whose wallet could not pay to claim an HTLC. It also gives `policy`, the policy with the defaults it took, and `feeCoins.readyCoinSatoshis`, the value of each ready coin: a fee coin is spent whole, so what the ready coins pay for is counted coin by coin. A node that forwards asset HTLCs adds `reserve`, what it keeps for its spends with a deadline (see "How many HTLCs an asset channel carries at once"). Asking makes no split and changes nothing, and the answer is `undefined` on a node without a fee policy. That answer has `available: true`. When the wallet refused the policy the answer is `{ available: false, error }`, the error being the `FEE_POLICY_REFUSED` refusal. It is read only beside `auxiliaryChannels`, and without it the wallet prepares no fee coins and chooses coins exactly as it does on a node with no extension.
- **The rate of a split, and a deadline.** A split pays the rate of the transaction it is made for (the node's rate for that spend, rounded up to a whole sat/vB), never less than `preparationFeeRatePerVbyte` and never more in all than `maxPreparationFeeSatoshis`: when the rate asked does not fit that cap, the split pays the highest rate that does. Its input says it may be replaced. While a spend waits on a split that has not confirmed, the pool replaces the split by one that pays more: in the next block when the spend is asked at a higher rate than the split pays, otherwise 6 blocks after the split went out, or 2 blocks when the spend has a deadline within 18 blocks (the distance at which the node closes a channel to claim an HTLC). A replacement pays the rate of the spend or half as much again as the split it replaces, whichever is more, within the same cap, and at least 1 sat/vB of its own size more in all. It has the same fee coins at the same positions, every fee coin the pool or an action held follows it, and the budget is charged the difference. A split one of whose fee coins was spent is not replaced. A fee coin that the wallet no longer lists leaves the action it was pledged to and another takes its place, unless it is an input of a transaction the action is replacing that the wallet's server knows; a spend that was refused for a coin spent elsewhere is therefore funded from another coin at the next raise, and the action's record keeps the coin it let go of, which is charged at retirement only if the transaction that settled the output spent it. A retirement the wallet refuses is tried again on the next block and after a start. A fee action opened for an output of a commitment that was seen and did not confirm is retired once the commitment that confirmed in its place is settled for good: it is charged nothing and its coins go back to the pool. When a block takes a split that was replaced, its fee coins are held under its id again and the budget is charged what that split paid. A claim by preimage has a deadline, the expiry of its HTLC: the wait in `getChannelMonitorState` (`auxiliaryFeeWait.deadlineHeight`) and `getFixedOutputFeeStatus().lastRefusal.deadlineHeight` carry it. On a node that forwards asset HTLCs, the timeout of a forward's outgoing asset HTLC has a deadline too: the incoming HTLC's expiry, less the distance at which the node takes the incoming channel to the chain (twice the safety margin, and at least 18 blocks for an incoming asset leg), less `ASSET_FORWARD_FAIL_BACK_DEPTH`, so that the incoming leg is failed back in its channel before then. The node works it out from its forward links on each block and after a start and keeps it in memory only; such a spend is raised every 2 blocks within 18 of its deadline, not every 6, and once it is past, the node says the incoming channel goes to the chain unless the timeout is 6 blocks deep by the incoming HTLC's own deadline. When the deadline is within 6 blocks and no confirmed fee coin is ready, the claim takes a coin of the pool's own split before the split has confirmed, in the same call that sent the split, so both can be in one block. A coin that is not of the pool's own split is never taken unconfirmed. From the block of the deadline on, a wait whose remedy was `wait` reads `none`, its message names the deadline, and the node emits one `error` that says the peer can now take the output back; the spend still goes out as soon as a fee input is there. The numbers are `FIXED_OUTPUT_FEE_TIMING`.
- **The child of a commitment.** A node that closes an asset channel by force bumps its commitment with a child that a coin of the wallet pays for, not a fee coin, and that coin is held for as long as the child can confirm. When the funding output is spent in a block, the coins the node's children took are free again in the handling of that block. When the transaction in that block is not the commitment the node was bumping, that commitment and its children are no longer offered to the network either. The node keeps the list of those coins while it runs: a node that stopped between building a child and that block leaves the coin to the wallet's own expiry of such holds.
- **`bind(node)`** is called once per build with that build's `LightningNode`, as soon as it is constructed and before it restores its stored channels: no hook of `auxiliaryChannels` runs before it. It runs outside any storage transaction and before any `start()`. The node has restored and started nothing yet, so keep it and ask nothing of it there. It is synchronous: a promise it returns is not waited for. An in-process rebuild attaches again and binds the new node to the new attachment, so keep no node from one generation for the next.

A daemon whose database holds asset channels does not start without the provider that runs them. It answers `ASSET_PROVIDER_REQUIRED` and changes no stored row, so the same database starts once the extension is named again. Signing for such a channel as an ordinary one would leave the asset out of the commitment.

## Feature detection

- `GET /extensions` (scope `readonly`; CLI `beignet extensions`) answers `{ api, extensions }`. An engine without the contract answers `404`.
- A supervisor that decides whether to name an extension before it starts the daemon can look for the literal `beignet-extension-api/1` in the installed `dist/cli/extension.js`.
- The asset channel members have no marker of their own. An extension that supplies them finds out at run time: `bind` is called before `start()` on an engine that reads them, and never on one that does not.

## The cooperative close of an asset channel

An asset channel is a channel a host's asset provider keeps state for. Its cooperative close is the engine's taproot close in one round: the opener proposes a fee, and the other node signs the same transaction or refuses.

**The fee a node accepts.** The node that answers a proposal accepts a fee inside a band it builds from its own live closing feerate (the fee estimate it would propose with itself, never below the channel's commitment feerate) and the weight of the closing transaction with the provider's outputs:

| Bound | Value |
| --- | --- |
| Lowest fee | the relay floor for the transaction's weight (253 sat/kw) |
| Highest fee, paid by the peer | ten times the node's own estimate |
| Highest fee, paid by this node | twice the node's own estimate, and never more than its balance less the dust limit of its own output |

A fee outside the band is refused locally: nothing is signed, the peer is not sent an error, the channel stays in `NEGOTIATING_CLOSING`, and a reconnect starts a new round with a new proposal. A fee that would take this node's output below its dust limit, or that the opener's balance cannot pay, fails the channel as on any other taproot channel. An ordinary channel keeps the engine's own band, built from the commitment feerates.

**A close the node did not sign.** Every spend of the funding output that is not a commitment transaction ends the channel as a cooperative close, also a transaction this node never signed and so holds no asset payload for (`closeTransactions` has no entry for its txid). The channel still ends as `CLOSED`, and the node says which transaction that was: `auxiliaryState.unrecordedCloseTxid` holds its txid in the channel's row, and the `channel:closed` event carries `unrecordedCloseTxid` beside `channelId`. The event fires once, at the close; after a restart the row still holds the txid and the event is not repeated. For a close the node signed, the field is absent from both. The chain monitor's record of the spend says the same: `getChannelMonitorState(channelId).commitmentBroadcast` is a `COOPERATIVE_CLOSE` record with `unrecordedClose: true`, on the running node and after a restart, and the record of a close the node signed has no such key.

## Asset channels in a program that embeds the engine

A program that embeds the engine can give its Lightning node an auxiliary channel provider (`INodeConfig.auxiliaryChannels`, an `IAuxiliaryChannelConfig`), and the node then holds asset channels: channels that carry asset units beside bitcoin. That is set where the node is made, not through the extension contract above, whose version 1 does not include the Lightning node. The options a host sets beside the provider are fields of the same object. This section lists the ones that bound what a channel holds, and what a host should watch.

### Asset IDs and balances

A channel can hold a single asset ID, including an ungrouped one. When it holds several IDs, they belong to one group. The provider tracks the IDs and assigns each ID's units to commitment outputs in the order the engine supplies. The engine keeps one balance per side and one amount per asset HTLC. Each is the sum of the units across the IDs it covers. For an HTLC, the provider returns this sum from `getHtlcAmount`.

The signatures for all HTLCs and the provider's custom records must fit in one `commitment_signed` payload. The engine checks the size of the signed payload before recording the signature state or sending the message. The commitment tests use synthetic records sized for three asset signatures per HTLC, with three IDs of one group and 83 HTLCs in each direction. They cover both the basic overlay and the channel type with child custody.

### How many HTLCs an asset channel carries at once

`auxiliaryChannels.maxHtlcs` is the most HTLCs the node holds open at once on an asset channel, each way. It is a whole number from 1 to 83 and is 8 when the host does not set it; a node given any other value refuses to start.

- **What the node accepts.** On every asset channel it opens or accepts, the node announces this number as its `max_accepted_htlcs`. A peer that adds one HTLC more has broken the protocol and the channel fails, as on any channel.
- **What the node offers.** The node never has more than this many asset HTLCs of its own open on one asset channel, whatever the peer announced it would accept. The next asset payment is refused before anything is recorded or sent, with an `AuxiliaryPaymentError` whose code is `ASSET_HTLC_LIMIT_REACHED`; send it again once one of the open HTLCs has ended.
- **Channels that exist already.** What a channel announced when it was opened cannot be taken back, so a channel opened under another number still accepts what it announced then. The bound on what the node offers is read from the present setting and applies to every asset channel at once.

The reason for a small number: when a channel goes to the chain, every HTLC that is open is an output the node may have to spend before a deadline, and each of those spends takes its fee from fee coins of its own, spent whole. A node that makes and receives single payments needs a handful at once, and prepares its fee coins when a claim asks for them, a few per preparation and a block each.

A node that forwards asset HTLCs (one whose host supplies `prepareForward`) holds more, and keeps fee coins ready for them:

- **The coins it keeps.** On each block, unless a spend is being given fee coins or waits for one, the node asks its pool to prepare coins ahead of any claim (`prepareFixedOutputFees`): as many as its spends with a deadline need now, plus `feeCoinCount`. Each is the fee of the largest such spend with one fee input, 308 vbytes, at the node's fee estimate, or at 10 sat/vB without one, and never under `preparationFeeRatePerVbyte`. `getFixedOutputFeeStatus().reserve` says that size (`coinSatoshis`) and its rate, how many spends with a deadline the coins must cover (`need`, `revoked` of them penalties), how many the coins ready pay for (`fundable`) and the `shortfall`. The spends with a deadline are the claim of a received HTLC, the penalty of an output of a revoked commitment of the peer or of its second-level transaction, and the timeout of a forward's outgoing asset HTLC; before a channel is on the chain, each of its asset HTLCs counts. While a kept coin would be over `maxFeeSatoshis`, none is prepared, since no fee action could spend it, and forwards are refused until the rate falls.
- **Spends without a deadline wait.** The sweep of a second-level output and the timeout of an HTLC of the node's own payment ask for fee coins only 6 blocks (`FIXED_OUTPUT_FEE_TIMING.noDeadlineAskBlocks`) before they can confirm, and only from coins beyond those the spends with a deadline need; until then their wait says `FEE_KEPT_FOR_DEADLINES`. With no spend with a deadline waiting they ask as before. A penalty never waits.
- **What a forward needs.** A forward with an asset leg is taken only while the coins ready pay for every spend with a deadline and for the forward's own asset HTLCs, and the budget has room for them (see "What the engine checks whatever the host answers").
- **HTLCs that end at the node.** With `requireFeeCoinsToSettle`, an asset HTLC that ends at the node is taken only while the coins ready would pay to claim it with the others: a payment of one HTLC is failed back with `temporary_node_failure`, and `settleHeldHtlc` throws `FEE_COINS_SHORT` (remedy `wait`) and keeps the parts held. Without it such an HTLC is taken as before and a shortfall shows in `reserve`. The node's own payments are never refused for it: the peer can take an offered HTLC only with its preimage, which pays the payment.
- **The sizing.** For a channel of N HTLCs each way the node needs, on the chain: 2N fee coins of the kept size R; a lifetime budget of 2N times R, twice that for the outputs of a revoked commitment, whose second-level race may call for a second penalty, plus one action's cap; ordinary wallet funds for the child that bumps the commitment (968 + 172 times 2N weight units at the rate it is bumped at); and the channel's bitcoin for the carriers and the commitment's own fee. At 10 sat/vB R is 3,080 sat, so a channel of 20 a side needs 40 coins of it, 123,200 sat, and a budget of 123,200 sat plus a cap. The node prepares at the rate of the moment: when fees rise, its coins pay for fewer spends and it prepares more at the higher rate, each split's own fee held to `maxPreparationFeeSatoshis`, which makes fewer coins at once as the rate rises; a larger `feeCoinCount` (16) makes more. Every raise of a spend takes one more coin.
- **Shown on the chain** with 20 HTLCs each way on a channel of the fixed mode, both nodes forwarding (`npm run test:full-channel`): a channel full at that number that goes to the chain by the node's commitment and by the peer's, with every claim confirmed before its deadline and every timeout after its expiry, and a revoked commitment of the peer that carries all of them, with every output punished within a few blocks; in each, the fee coins came from the node's preparation. Above 20 the sizing holds, and nothing above it was run.
- **An open or accept above 8 that the policy cannot cover** is refused before anything is recorded or sent: with `FEE_ACTION_CAP_EXHAUSTED` when a kept coin is over `maxFeeSatoshis`, and with `FEE_BUDGET_EXHAUSTED` when the budget left cannot hold twice `maxHtlcs` kept coins and one cap. A node never refuses to start over it: one that holds channels has to start to defend them. At 8 or below nothing is refused, and a shortfall shows in `reserve`.

Ordinary channels are not touched by this setting.

### The store of revoked views grows for as long as the channel lives

For every commitment of the peer that the peer has revoked, the node keeps the asset side of that commitment (its view) in a store of its own, so that it can punish that commitment should it ever be published. Nothing in this store is ever trimmed while the channel lives: any revoked commitment may still reach the chain, and each has to stay punishable. The store therefore grows by one row with every commitment the peer revokes, which is every payment over the channel, in either direction, and it is dropped only with the channel.

A host reads how large it has grown from `getAuxiliaryChannelInfo(channelId).revokedViews`, which answers `{ rows, bytes }`: the number of views kept for the channel and the bytes their values take in the database. The field is present when the node's storage keeps this store, which the SQLite backend does. The table is counted once, the first time a channel is asked about; after that every write of a view keeps the answer current, so reading it is cheap however large the store is. A host that plans its disk, or that wants to tell its user when a long-lived channel is worth closing and opening again, goes by this number.

## Forwards with an asset leg

The node runs this part from the build whose `AUXILIARY_CHANNELS_API.surfaces` names it as `prepareForward`, and a host relies on it from that build on. Builds before it named the part in `declared`, which names a part the build does not run, or runs only in the part its documentation names, with no effect a host may rely on, and refused every forward with an asset leg before anything was offered, whatever their host supplied.

A forward has an asset leg when either of its HTLCs belongs to an asset channel. The incoming leg is an asset leg when its HTLC carries units or came in on an asset channel. The outgoing leg is an asset leg when it leaves over an asset channel, which offers no HTLC without units. A leg that is not an asset leg is a bitcoin leg. That makes three directions: bitcoin in and asset out (a wallet behind the node is paid), asset in and bitcoin out (a wallet behind the node pays), and asset in and asset out (two wallets behind the node that hold the same asset).

Two optional members of `IAuxiliaryChannelConfig` carry it, with the types of `src/lightning/channel/auxiliary-forward.ts`:

```ts
prepareForward?(request: IAuxiliaryForwardRequest): IAuxiliaryForwardTerms | undefined;
onForwardLegResolved?(resolution: IAuxiliaryForwardLegResolution): void;
```

A host takes part by supplying `prepareForward`. A node whose host does not supply it asks nothing and refuses every forward with an asset leg, as it does today, in every build. `valueIncomingHtlc` stays the hook of an HTLC that ends at the node: a forward is never put to it.

### Which HTLCs the host is asked about

An HTLC the node received and is not the final hop of, once it is irrevocably committed and has passed the checks the node makes of every forward before it looks for the next hop (the limits on HTLCs in flight and on a peer's rate, the onion, the expiry against the tip, forwarding being on), when either:

- one of its legs is an asset leg: it carries units or came in on an asset channel, or the short channel id the onion names is one of an asset channel of the node, by an alias or, when the channel's type lacks `option_scid_alias`, by its real id; or
- the short channel id the onion names is not one the node knows: no channel of the node has it, and the node's JIT receive did not mint it. The hint of an asset invoice names a short channel id made from a quote's id, and only the host that gave the quote can recognise it, so the host is asked about every such id, also for an HTLC that carries no units.

A forward inside a blinded path is not asked about: one with an asset leg is refused, and one whose short channel id the node has no channel for fails as it does today. Neither is a forward with an asset leg that the onion asks the node to hold for an offline receiver, which is refused. Nor is an HTLC that came in on an asset channel and carries no units. It holds nothing but bitcoin, so it is refused rather than valued by the host, whose value could then overstate what the node received. Nor is a forward to the real id of a channel whose type has `option_scid_alias`. BOLT 2 forbids forwarding over such a channel by that id, so the node fails it with `unknown_next_peer` as it does today, and a host's hint names one of the channel's aliases. Nor is a forward to a short channel id the node's JIT receive minted, whether or not the receive takes the HTLC: one with an asset leg is refused, and one without goes to the JIT receive as today. Nor is an HTLC that came in on an asset channel whose onion names that same channel: asset in and asset out goes between two asset channels of the node, so it is refused. The node's own payments are not forwards, and nothing here changes them.

`IAuxiliaryForwardRequest` gives the payment hash; the incoming HTLC (`incoming`: its channel, peer and id, the bitcoin it carries on the wire, its expiry, its units and custom records when it has them, and whether its channel is an asset channel); what the onion asks (`shortChannelId`, `amountToForwardMsat`, `outgoingCltvExpiry`); and `outgoing`, the node's channel that the short channel id names, absent when the node has none. The host reads anything more about either channel through the node: `getChannel` for any channel, and `getAuxiliaryChannelInfo` for an asset channel.

### What the host may answer

- **Its terms** (`IAuxiliaryForwardTerms`), with exactly the fields the forward's legs call for and no other:
  - `outgoingChannel`, when the request has no `outgoing`: the asset channel the short channel id stands for, and its peer. It is not the channel the incoming HTLC came in on.
  - `incomingValueMsat`, when the incoming leg is an asset leg: what the incoming HTLC is worth, in millisatoshis, above zero and within a u64.
  - `outgoingHtlc`, when the outgoing leg is an asset leg: the custom records of the outgoing HTLC (at least one, each of a type at or above 65536) and its carrier, the bitcoin it carries on the wire (`wireAmountMsat`). The host makes the records hold units worth `amountToForwardMsat` at its own rate. The engine cannot value them; the next hop judges them, as the wallet behind the node judges an HTLC against its quote.
- **`undefined`**, "not mine": only for a forward with no asset leg, whose short channel id the host does not know. The node goes on exactly as without a provider and fails the HTLC back with `unknown_next_peer`. For a forward with an asset leg it refuses.
- **A throw**: the incoming HTLC is failed back with `temporary_channel_failure`, and nothing is offered.

Anything else refuses as a throw does: a field the forward does not call for, a missing one, a value out of range, records that are not custom records, a channel that is not an asset channel of this node with the peer named, and a promise. The hook is synchronous. A host that answered with terms is told how the forward ended in every case, also when the node refused the terms as malformed or a check below refused the forward, so that it can let go of what it reserved. A host that threw or answered `undefined` took nothing on and is told nothing, save after a stop (below).

### Asked once

The host is asked once for each incoming HTLC, synchronously, outside any storage transaction, and before anything is offered. The node keeps the answer with the forward, written before the outgoing HTLC is offered or with it, and when the forward is gone through again (a reestablish, a restart) it reads the answer back and does not ask again, as the value of a held HTLC is asked once. Before it asks, the node writes that it is asking about the HTLC. A node that stopped after that write and before the answer was written asks again when it comes back, with the same request, if the incoming channel can still settle the HTLC and the forward still passes the checks made before the ask. Otherwise it offers nothing and tells the host the outgoing leg was never offered, whatever the host answered before the stop. The tip may have passed the outgoing expiry meanwhile, and the HTLC is failed back. Or the incoming channel was closed on the chain while the node was down, and the chain resolves the HTLC. So a host keys what it reserves for a forward, a quote for instance, by the incoming HTLC (`incoming.channelId` and `incoming.htlcId`), and answers a second ask about an HTLC as it answered the first.

A quote prices one payment. Each HTLC is a forward of its own, and whether a quote that priced one HTLC may serve another is the host's to decide.

### What the engine checks whatever the host answers

The answer lifts none of the node's checks of a forward. The node offers the outgoing HTLC only when all of these hold, and otherwise fails the incoming HTLC back. A check that needs no answer is made before the host is asked, so a forward it refuses is never put to the host; one refused after the host answered with terms is told to the host as an outgoing leg never offered.

- **Both channels.** The incoming HTLC is irrevocably committed before the outgoing one is offered: the node neither asks nor offers before then. The outgoing channel takes a new HTLC, as for any forward: it is open and not quiescing, its state can be proven current and its funding is accounted for. When both legs are asset legs, they are on two different channels.
- **The expiry deltas.** The outgoing expiry is more than 3 blocks above the tip, the incoming expiry is no earlier than the outgoing one plus the CLTV delta of the outgoing channel's policy, and the incoming expiry is no further ahead than the node accepts of any HTLC.
- **The HTLC limits.** The peer's `max_accepted_htlcs`, `max_htlc_value_in_flight_msat` and `htlc_minimum_msat` on the outgoing channel; for an outgoing asset leg, the node's own bound on the asset HTLCs it offers at once (`maxHtlcs`) and on outcomes its host has not taken; and the node's bound on HTLCs in flight across its channels.
- **The reserve.** The node's bitcoin on the outgoing channel covers what the HTLC carries on the wire, above the reserve its peer requires and the commitment fee the node pays as the funder.
- **The carrier of an outgoing asset HTLC.** It is above zero and at least the larger of the channel's two dust limits, so that the HTLC has an output of its own on both commitments; the provider admits its records (`validateHtlc`) and reads units from them (`getHtlcAmount`); and the node holds those units on the channel.
- **The fee.** What the incoming leg is worth covers the amount to forward and the node's fee on it, from the outgoing channel's policy, as for any forward. A bitcoin leg is worth what it carries. An incoming asset leg is worth the host's `incomingValueMsat`. The outgoing leg is worth `amountToForwardMsat`, whatever it carries on the wire.
- **The delta of a forward with an asset leg.** The incoming expiry is at least `ASSET_FORWARD_MIN_CLTV_DELTA` (40) blocks above the outgoing one, whatever the outgoing channel's policy allows, or the forward is refused with `incorrect_cltv_expiry`. An outgoing HTLC that times out on the chain is spent there a few blocks past its expiry at the earliest, and the incoming leg is failed back once that spend is 6 blocks deep (below): about 14 blocks past the outgoing expiry with a fee coin ready. An incoming asset leg whose outgoing leg is unresolved goes to the chain 18 blocks before its own expiry. Below about 33 blocks the second comes first, and the incoming channel would be closed for a forward that failed.
- **The fee coin pool.** For a forward with an asset leg on a channel of the fixed mode (feature 451), the node reads its pool before the host is asked (or, for a quote, once its channel is known) and refuses with `temporary_channel_failure` unless the fee coins ready pay, each spend with whole coins at the node's rate, for every spend with a deadline the node may have to fund (each asset HTLC of its channels of that mode, the forward's incoming HTLC among them when it came in on one, and each such spend of a channel already on the chain) and for the asset HTLCs the forward would offer, and unless the budget has room for all of them at the size of a kept coin, the penalties of a revoked commitment twice, plus one action's cap. A split not yet made counts for nothing: the node prepares its coins ahead, on each block. It refuses as well when there is no pool, the wallet refused its policy, or its status does not say what its coins are worth. It reads the pool and reserves nothing: every path runs from this look to the add in one synchronous turn, so forwards that arrive together are counted against each other.
- **Ends not taken.** A channel holding `ChannelManager.AUXILIARY_MAX_UNDELIVERED_OUTCOMES` (1,000) ends of forward legs that its host has not taken (`IAuxiliaryChannelInfo.undeliveredForwardLegEnds`) takes no forward with an asset leg, in or out.

No check that compares what a leg is worth in millisatoshis applies to the wire amount of an asset leg as it stands: that amount is a carrier, the few hundred satoshis that keep the HTLC's output on the commitments, and not what the leg is worth. The carriers are the host's to price: the node takes the incoming HTLC's carrier when the forward settles, so it is part of what that HTLC is worth to the host, and it pays the carrier the host made for the outgoing HTLC, which is part of what the host gives for `amountToForwardMsat`. The node does not weigh one carrier against the other. The carrier is held only to the rules of its channel's own bitcoin above (the dust limits, the reserve, the peer's minimum and its bound on value in flight), as any HTLC is. Where an ordinary forward answers with a failure that quotes the amount of the incoming HTLC (`fee_insufficient`), a forward whose incoming leg is an asset leg answers `temporary_channel_failure`, so that a carrier is never quoted as what an HTLC is worth.

The fee and the CLTV delta are those of the outgoing channel's policy (`setChannelPolicy`, or the node's defaults), as for any forward. A host whose quotes advertise their own terms in a route hint, a zero fee and a CLTV delta of 40 for instance, sets them as the policy of the asset channels its quotes lead over. A quote cannot lower the delta below that policy.

### When each leg ends

A forward with an asset leg ends as any forward does, whichever of its legs holds units:

- A preimage the outgoing leg gives up, in `update_fulfill_htlc` or in a spend on the chain, claims the incoming leg: by `update_fulfill_htlc` while the incoming channel can carry it, and on the chain otherwise. For an incoming asset leg the node writes its decision to settle with the incoming channel's row as soon as it learns the preimage, so that a claim on the chain is made for that HTLC: a decision that waits on another channel.
- An outgoing leg that failed fails the incoming leg back: failed in its channel, never offered, or timed out on the chain once that spend is `ASSET_FORWARD_FAIL_BACK_DEPTH` (6) blocks deep at a height the node has seen reported since it last started, with no preimage learned. An ordinary forward waits until such a spend is irrevocable; with the delta of a quote that would come after the incoming deadline. So does an outgoing leg on an asset channel that is on no output of the commitment that confirmed (an HTLC the peer had not signed in yet, or any HTLC of a revoked commitment of the peer), once that commitment is that deep. The risk taken is a reorganisation deeper than 6 blocks that puts the peer's claim by preimage in the place of the timeout. An outgoing bitcoin leg on no output of the commitment that confirmed (a trimmed HTLC) cannot be read off the chain: its incoming leg goes to the chain at its deadline, and the payer takes it back there. Such a leg ends `failed` on the chain.
- An incoming HTLC whose expiry comes near while its outgoing leg is unresolved takes its channel to the chain, so that a preimage learned late still claims it: twice the safety margin before its expiry for a bitcoin leg, as for any forward, and `INBOUND_HTLC_CLAIM_FORCE_CLOSE_BUFFER` (18 blocks) for an asset leg, whose claim takes a fee coin, also while its peer is away or a shutdown is under way. An incoming asset leg already on the chain is never given a decision to fail, so that a preimage a deeper reorganisation brings to light still claims it.

The host is told of each leg as it ends, through `onForwardLegResolved` (`IAuxiliaryForwardLegResolution`): the forward, by its incoming HTLC; which leg; its channel and its HTLC's id; how it ended (`fulfilled`, `failed`, or `never-offered` for an outgoing leg whose HTLC never entered its channel); whether it ended on the chain; for an asset leg, the units and the custom records its HTLC carried; and the quote the forward was taken under, as the node knows it: `shortChannelId`, the next hop the onion named (for a forward by a quote, the short channel id the host claimed for it), and `valueMsat`, what the leg was worth as the node counted it (the host's value of an incoming asset leg, the amount of an incoming bitcoin leg, the amount to forward of an outgoing leg, never offered included). The node keeps both on the HTLC entries from the ask on, with writes it makes anyway: the next hop and the amount to forward with the mark that it asks, the worth with the mark that the host took the forward on, all three with the outgoing HTLC's add. So `valueMsat` is absent on an incoming asset leg whose terms were refused as malformed, or whose answer a stop lost before it was kept, and both are absent on the end of a forward that a build before them asked about. After a stop, a second ask that values the incoming leg otherwise is what its end tells. A leg ends when its HTLC has left its channel for good, its removal irrevocably committed, or when the chain has resolved it, which is at irrevocable depth (100 blocks), as for `onHtlcResolved`. As with `onHtlcResolved`, an incoming asset leg told `fulfilled` is told again, as `failed` with `preimageRevealed: true`, when the payer took the output back on the chain after the node had claimed it; a bitcoin leg carries no `preimageRevealed`. The call is synchronous and made outside any storage transaction, and it is durable: what it reports is kept in the row of the leg's channel and offered again, after each write of that channel, on each block and after a restart, until a call returns without throwing. The two legs end in no promised order. A host without `onForwardLegResolved` is kept nothing. `onHtlcResolved` keeps its own rules for asset HTLCs, the leg of a forward or not.

### In the forwarding history

A forward with an asset leg is written to the forwarding history (`listForwards`, the daemon's `GET /forwards`) where an ordinary forward is: when the fulfil its outgoing leg received in that leg's channel settles the incoming leg. A preimage learned on the chain, or a fulfil retried after the outgoing HTLC has left its channel, writes no row for either kind. The row is marked `auxiliary: true`, and its amounts are what each leg was worth, never a carrier. `amountInMsat` is the host's value of an incoming asset leg or the amount of an incoming bitcoin leg, `amountOutMsat` the amount the onion asked the node to forward, and `feeMsat` their difference, which the engine's own checks hold at or above the outgoing channel's fee. That is the reverse of a payment record, where the amount is the carrier and `auxiliaryValueMsat` the worth: here the fee stays in less out, and a build that does not know the mark reads sensible amounts. Beside them the row keeps each asset leg's units and carrier (`inAuxiliaryAmount` and `inWireAmountMsat`, `outAuxiliaryAmount` and `outWireAmountMsat`) and the next hop the onion named (`nextHopScid`, hex).

The node's `htlc:forwarded` event and its `htlc/forwarded` log carry the same, and `htlc:forward-refused` of such a forward carries `auxiliary: true`. `getForwardingSummary` counts such forwards apart, in `auxiliary`, present only when there is one, so that its bitcoin totals count ordinary forwards only. The fee tuning of an ordinary channel (`autoTuneFees`) counts a forward with an asset leg that crossed it like any forward, since that channel's bitcoin moved, and still leaves asset channels alone. A storage backend of the program's own keeps these fields and splits its summary the same way (`IForwardingStorage`, checked by `runStorageConformanceSuite`).

The SQLite database is at schema 21 from this build: `forwarding_events` gains one column, `auxiliary_json`, empty for every ordinary forward, on every node with or without asset channels. A build before it opens such a database, lists a forward with an asset leg as an ordinary one at what its legs were worth, counts it in its own totals, and writes its own rows with the column empty.

### A gate for whoever wraps the node

A program that wraps the node can refuse a forward with an asset leg before anything of it is offered, as `setAuxiliaryPaymentGate` lets it refuse an asset payment: `setAuxiliaryForwardGate(gate)`, and `undefined` to remove it. The node asks the gate once for each offer, synchronously: after the host's terms are read and the forward's checks before the add have passed (the look at the fee coins of a channel of the fixed mode among them), and before the link is staged and the outgoing HTLC added.

The gate is given copies (`IAuxiliaryGatedForward`): the payment hash; the next hop the onion names; the incoming HTLC (its channel and peer, its id, the bitcoin it carries, its units, what it is worth, and whether it came in on an asset channel); the outgoing HTLC about to be offered (its channel and peer, the bitcoin it is to carry, what it is worth, and whether it leaves over an asset channel, but not its units, which the provider reads from the host's records at the add); and the node's fee. It answers `undefined` to let the forward through, or the reason it is refused, as a string or as `{ reason, message }` with its own stable code. One that throws, or answers with a promise, refuses.

A refused forward offers and links nothing: its incoming HTLC fails back with `temporary_channel_failure`, the host is told that the outgoing leg was never offered, and the structured log `asset_forward_declined` says why, with `gateReason` when the gate gave a code. What the node wrote of the ask stays, as after any refusal that follows the host's terms: the marks of the ask with the terms they keep, the never-offered end, and an incoming asset leg's decision to fail. The gate is never asked about an ordinary forward, nor about one the host does not take or the node's own checks refused before it. The checks of the outgoing channel at the add come after it, so a forward it lets through may still be refused there. It runs between the node's look at its fee coins and the add, so it must not act on the node.

### Going back to an earlier build

A node is taken back to a build without this part only with no forward with an asset leg in flight and no end of one its host has not taken: its host stops answering `prepareForward` and it waits until `getAuxiliaryChannelInfo` reports no `forwardsInFlight` and no `undeliveredForwardLegEnds` on any asset channel. A daemon does both with a drained stop (`POST /stop` with `drain`), given a `drainTimeoutMs` long enough for the forwards in flight to end. Such a build keeps none of the ends the host has not taken yet.

## How a wallet learns which assets its primary offers

Asset channels stay private from opening through every splice. The engine never announces either funding output. The BOLT 7 `channel_announcement` verifies a 2-of-2 P2WSH output. An asset channel uses a Taproot output, and its value in satoshis does not tell a payer how many units of an asset can cross it. [BOLT 7 channel announcements](https://github.com/lightning/bolts/blob/master/07-routing-gossip.md#the-channel_announcement-message)

For discovery, the host should send its connected wallets the asset IDs its node offers. This list is planned host work. A wallet uses it to choose an asset and request a quote. Payers can reach the primary over its ordinary announced Bitcoin channels, then use the quote's invoice route hint for the private leg. The list exposes no channel IDs, funding outpoints or balances. [What an asset invoice advertises](#what-an-asset-invoice-advertises)

Public asset routing would require a separate decision and a gossip format that can verify Taproot funding. This discovery decision adds no engine wire message or stored state and has no effect on downgrade.

## What an asset invoice advertises

The node runs this part from the build whose `AUXILIARY_CHANNELS_API.surfaces` names `createInvoice:assetInvoice`, and a host passes the field to such a build.

An asset invoice is paid with asset units over the node's asset channels, through the routing hints its host gives: the hint of a quote, for instance, whose short channel id only the peer that gave the quote recognises. The host makes one with `createInvoice`, passing those hints in `extraRoutingHints` and `assetInvoice: {}`. The invoice then carries only those hints, never one the node builds from its own channels: a payer that took such a hint would send a plain HTLC, which is the host's to refuse. The engine records nothing of the mark. The invoice's record is any invoice's, its `auxiliary` is set only once asset HTLCs pay it, and a plain HTLC that pays it is still the host's to refuse through `valueIncomingHtlc`.

### When it offers basic_mpp

An asset invoice offers basic_mpp only where its parts can be collected, that is when all of these hold:

- the node collects the parts of an asset payment: its host sets `receiveInParts: true`, and basic_mpp is among the node's own features (`localFeatures`), as it is by default;
- it is no hold invoice, which stays paid by one asset HTLC;
- every hint ends at one peer, since a set is all one peer's parts;
- that peer's asset channels with the node that take HTLCs, now or once the peer is back, can hold two at once toward the node: each holds the fewer of the HTLCs the node accepts and those the peer accepts (a peer of this engine offers no more asset HTLCs at once than its own `maxHtlcs`, which it announces as its `max_accepted_htlcs`), and together they hold at least 2;
- the host did not pass `inParts: false`, which is for an invoice through a peer that does not forward the parts of one payment under its quote.

Otherwise it does not offer basic_mpp, and a payer pays it by one HTLC, as BOLT 4 has it. Every other feature is as for any invoice: TLV onion and payment secret compulsory, and payment metadata when given. `receiveInParts` is read at each part, while an invoice keeps what it offered: a host turns `receiveInParts` off once the asset invoices that offered parts have expired, since their parts are failed back from then on. A host that pays splits only an invoice that offers basic_mpp.

### Refusals

Each comes after the checks any invoice gets (its description, a JIT fee allowance's values, the size of payment metadata, and a hold invoice's external payment hash) and before anything is kept (no preimage, payment secret, hold mark or record, and no random byte drawn), as an `AuxiliaryInvoiceError` with a `code` and the `option` at fault, in this order:

- `ASSET_INVOICE_INVALID` for `assetInvoice`: the field is neither an object nor left out (`undefined`, `null` and `false` make an ordinary invoice), or its `inParts` is not a boolean;
- `ASSET_INVOICE_UNSUPPORTED` for `assetInvoice`: the node has no asset channels configured (`auxiliaryChannels`), or its host gives no `valueIncomingHtlc`, without which every asset HTLC that pays the invoice is failed back;
- `ASSET_INVOICE_UNSUPPORTED` for the option named: `useBlindedPaths` and `asyncHold` (a blinded path is built from the node's own channels, and a blinded asset part is refused), `fforVoucher` (an invoice of its own kind), and `jitFeeAllowance` (an allowance applies only to an ordinary HTLC);
- `ASSET_INVOICE_INVALID` for `extraRoutingHints`: no hint, which an asset invoice needs even when only its direct peer will pay it; more than 20 hints, so that the invoice always fits its encoding; a hint of no hop or of more than 12; a hop that does not name a valid node id other than this node's, an 8-byte short channel id, fees from 0 to 4294967295 and a CLTV delta from 0 to 65535; a hint that does not end at a peer with an asset channel of the node that takes HTLCs now or once the peer is back, or that ends over an ordinary channel of the node, which the refusal names.

### Going back to an earlier build

Nothing new is stored: an asset invoice keeps its string, and its record is any invoice's. An earlier build settles one asset HTLC that pays it as before. One that collects no asset set fails back the parts of an invoice that offered basic_mpp. So before going back, a host stops passing the field, leaves `receiveInParts` out, and waits until the asset invoices that offered parts have expired.

## An asset invoice paid in parts

The node runs this part from the build whose `AUXILIARY_CHANNELS_API.surfaces` names it as `receiveInParts`, and a host relies on it from that build on. Builds before it named the part in `declared` (a part the build does not run, or runs only in the part its documentation names), or not at all, and failed back every HTLC that carries units and is a part of a set, whatever their host asked.

A payer on the network may split a payment whenever the invoice lets it. When the invoice is an asset invoice of a wallet behind a node that converts, every part reaches the wallet as an asset HTLC of its own under one payment hash. A host takes part by setting `receiveInParts: true` in its auxiliary channel configuration. The node then collects such HTLCs into one set, each at the value `valueIncomingHtlc` gives it, and settles them together once their values reach the total the payer declared. It does so only while basic_mpp is also among its own features (`localFeatures`), whose absence would stop the timer that fails a set that never completes. A host that leaves the field out keeps the refusal of earlier builds, its log included. The asset invoices a host makes offer basic_mpp only while the node collects their parts (see "What an asset invoice advertises").

### Which parts make a set

An HTLC that carries units is a part of a set when its onion declares a total above what the host valued it at, or when other parts of the hash are already collected. Parts are collected as any multi-part set is: each declares the same total, which lies between the invoice and twice it; a duplicate is ignored; a total that disagrees fails the whole set; and a set whose settled row would outgrow what a guardian accepts takes no further part. The set is complete when the values reach the declared total. Each part is refused before anything is kept, with `incorrect_or_unknown_payment_details` and the structured log `asset_multi_part_refused` with a `reason`, when:

- it would mix parts with units and parts without, either way round (`mixed`);
- the invoice is a hold invoice, which stays paid by one asset HTLC (`hold`);
- it comes from a peer other than the peer of the set's first part (`peer`);
- it is blinded (`blinded`);
- it declares no total while a set of the hash is being collected (`no-total`).

### What the host is asked

The host is asked about each part once for each dispatch, as about any HTLC that ends at the node. Its `acceptedHtlcs` lists the set's other parts still committed, each at the value the host gave it. The value it answers for a part is final for the set: the node sums the values and compares the sum with the declared total. Rounding is the host's to carry. A value may cover the shortfall the conversion of units leaves, a unit per part at most, when the host stands behind it, and a host that never covers it leaves such a set short until it times out. A set may name one quote or several: the node reads no quote. After a restart, a set that was not yet committed is collected again as its channels come back, and each part is valued afresh, with those collected before it in `acceptedHtlcs`; a part whose peer never returns is never collected again.

### Before anything is written

A complete set is settled only when every part can take its fulfil at once. Each part must be irrevocably committed in its channel under the hash, with nothing decided or owed for it, and more than the claim buffer (18 blocks, or the node's HTLC safety margin when that is larger) from its expiry. Each channel must be able to fulfil now, which a channel that is quiescing cannot, and must have no commitment on the chain. The provider must answer for the fulfils of each channel's parts, tried on a copy of the channel as each fulfil tries its own. A node that forwards with `requireFeeCoinsToSettle` also needs the fee coins ready to pay to claim them. Otherwise the whole set is failed back with `temporary_node_failure` (with `incorrect_or_unknown_payment_details`, each part's value and the height, when a part is too near its expiry), logged `asset_set_not_settled` with a `reason`, and nothing is written or revealed.

### The commit, and every part claimed

The set's records are then written alone, in one transition, before any fulfil: the payment COMPLETED with every part in `settledHtlcs`, `auxiliary: true`, `receivedMsat` the sum of the values, and `metadata._auxiliaryReceivedParts`, the value of each part by `<channel id hex>:<HTLC id>`; the invoice's `auxiliary` mark; and the deletion of the payment secret. A write that does not land fails the set back, with nothing revealed. From that write on, the set is committed and nothing gives it up, whatever `receiveInParts` says later:

- each part gets its decision to settle, written with its channel's row, and the preimage goes to the monitors, so that a close claims the part by preimage and nothing fails it back;
- each part's fulfil is made. One the provider refuses is made again by the node's periodic work, one the channel cannot carry now on its reestablish, and one never made on the next block;
- a decision that did not land is written again on each block, and at a restore before the node's first scan of its HTLCs; the engine keeps `_auxiliaryReceivedParts` as its own, as it keeps `_keysend`: `setPaymentMetadata` neither sets nor clears it;
- a part whose fulfil is still not made at the claim buffer is claimed on the chain by its decision, as the incoming leg of a forward is. That claim asks the same provider for its records, and needs fee coins: on a wallet, a set is taken as single payments are, and a shortfall shows in `getFixedOutputFeeStatus()`. A set adds no HTLC beyond what `maxHtlcs` admits on a channel already;
- the record stays while a part it names is open, also on a channel that has gone to the chain.

`payment:received` and `invoice:settled` come once, at the commit, and the host hears of each part through `onHtlcResolved` as of any asset HTLC.

### A part lost on the chain

A part the payer takes back on the chain after the commit leaves `_auxiliaryReceivedParts`, and `receivedMsat` is lowered by its value, in one write, so it is counted once. It is logged `asset_htlc_claim_lost` with a `node:error` coded `ASSET_HTLC_CLAIM_LOST`. The record stays COMPLETED while any part of the set was received, and turns FAILED, with `payment:failed`, only when every part was lost. A payment of one HTLC ends as before.

### A set that never completes

Each part of a set that does not reach its total within `mppTimeoutMs` is failed back with `mpp_timeout`, each fail owed and made again when it is refused, as for any multi-part set.

### Going back to an earlier build

Nothing new is stored but the metadata key, which every build keeps with the record. A set being collected lives in memory: after a restart an earlier build fails its parts back with the refusal it has. A committed set's parts are listed in its COMPLETED record, so an earlier build fulfils them on its restart and reestablish, and its monitor claims a part whose decision was written. An earlier build does not write a missing decision, does not claim at the claim buffer a part whose fulfil its provider keeps refusing on a channel that is open, and turns the whole record FAILED at the first part lost on the chain. So a node goes back only once no asset HTLC is left received: its host stops setting `receiveInParts`, and it waits until `getAuxiliaryChannelInfo` lists no HTLC with `direction: 'received'` on any asset channel.

## An asset payment sent in parts

The node runs this part from the build whose `AUXILIARY_CHANNELS_API.surfaces` names it as `sendInParts`, and a host relies on it from that build on. Builds before it named the part in `declared` (a part the build does not run, or runs only in the part its documentation names), or not at all, and refused every HTLC that carries units and is a part of a payment, whatever their host asked.

A wallet that holds units in one or several asset channels with the node it pays through can pay an invoice in parts, as a payer on the network splits a bitcoin payment. Each part is an asset HTLC to that peer, which forwards it on as a forward of its own; the payee collects the parts as any set. A host takes part by setting `sendInParts: true` in its auxiliary channel configuration. The host splits the payment: it sends each part by its own `sendPaymentToRoute` with `assetPayment`, choosing the part's channel, its route, its records, its carrier and the HTLC id it prepared them for, as it does for a payment of one HTLC. The node chooses no channel and retries nothing. Reading whether the invoice lets a payer split it (basic_mpp) is the host's: an invoice that does not offer it is paid by one HTLC. A host that leaves the field out keeps what earlier builds do: a part is refused (`ASSET_PAYMENT_UNSUPPORTED`), and every attempt of a payment names the one channel of its first.

### What a send of the host is checked against

With the field set, every asset HTLC the host sends takes this path, a payment of one HTLC included, which is a set of one. A part is a call whose total is above what its route's final hop receives (its value). Each refusal comes before anything is recorded or sent, as an `AuxiliaryPaymentError` that names the channel, in this order:

- the call's own checks, as for any asset payment: its records and carrier (`ASSET_PAYMENT_INVALID`), no pay-all and no retry of the node's own (`ASSET_PAYMENT_UNSUPPORTED`), and no hash that a pay-all holds (`PAY_ALL_BUDGET_MISMATCH`);
- the payment's record: a part is not sent to an invoice of this node, nor for a payment given up while a part of it is still out, by a cancel or by a part's expiry (`ASSET_PAYMENT_UNSUPPORTED`), nor for one already paid (`DUPLICATE_PAYMENT`, as before); once nothing of it is out a new set may start. A record whose parts cannot be read takes no part (`ASSET_PAYMENT_INVALID`);
- no mixing: an asset HTLC does not join a payment with an HTLC out that carries no units, nor one whose record is an ordinary payment still pending (`ASSET_PAYMENT_UNSUPPORTED`);
- the peer: every HTLC of the payment leaves over an asset channel of the peer of its first (`ASSET_PAYMENT_ROUTE_REQUIRED`); the peer's other asset channels may carry parts;
- the total: a part needs the payment secret, which carries the total in its onion; the total is never below the part's value; and a part declares the total the parts out declared (`ASSET_PAYMENT_INVALID`);
- the values: the values of the parts out and this one come to at most the total (`ASSET_PAYMENT_INVALID`). A value carries no fee, so the bound is exact; a payer that means to pay more declares a higher total, which a payee takes up to twice the invoice;
- the node's bound on its own asset HTLCs on the channel (`maxHtlcs`, `ASSET_HTLC_LIMIT_REACHED`) and on outcomes its host has not taken (`ASSET_OUTCOMES_UNDELIVERED`), as before: each part counts on its channel, and parts over several channels count on each;
- the route: no blinded path that starts at this node (`ASSET_PAYMENT_UNSUPPORTED`), and an asset channel to the route's first hop (`ASSET_PAYMENT_CHANNEL_MISMATCH`);
- the channel's own check of the carrier: the peer's `max_accepted_htlcs`, its bound on value in flight, the reserve and dust (`ASSET_HTLC_NOT_ADMITTED`);
- the onion, which must fit (`NO_ROUTE`), the payment's ceiling on its expiry (`CLTV_EXCEEDS_MAX`), and the HTLC id the host prepared the records for (`ASSET_PAYMENT_CIRCUIT_CHANGED`), as before;
- last the gate (`setAuxiliaryPaymentGate`), whose request then also carries `totalMsat`, the total the payment declares, and `htlcId`, the id the HTLC will take. Only the write of the record can fail after it (`ASSET_PAYMENT_NOT_RECORDED`), with nothing sent.

### Each part recorded before it is sent

The part is then written, in one write with its HTLC mapping and before its add: its value in `_auxiliaryPartAmounts`, as for any asset payment, and in `_auxiliaryPartsSent` what its route asked its first hop to carry, its carrier and the set it was sent in. `getAuxiliaryPaymentHtlcs` lists each such part with `routeAmountMsat` and `wireAmountMsat` beside its value, and `failed: true` once it has ended without paying. The payment's record is kept while a part of it is out, so its parts join one record: `amountMsat` is the carriers and `auxiliaryValueMsat` the values of the parts of its latest set that have not failed. A record that completed keeps the figures it completed with; one whose every part failed has those parts' figures. `setPaymentMetadata` neither sets nor clears these keys, nor, on such a record, the other keys of its asset HTLCs.

A part the channel refuses at its add, after it was recorded (the provider's own checks), never entered the channel: it leaves the record again with its mapping, and the send throws `ASSET_HTLC_NOT_ADMITTED`. When no other part of the payment is out, the record fails in that write and `payment:failed` comes before the throw.

### How the parts end

- **A part that settles:** the first completes the payment, with one `payment:sent`, as before. Every later one releases its own mapping.
- **A part that fails:** its failure is read with its own onion secrets, kept while the node runs (after a restart, with the record's, which are its set's first part's). It is marked failed in the record, whose figures leave it out. While another part of the payment can still settle, the record stays pending and only that part's end is told (`payment:htlc-resolved`); the last part to end gives the payment up, with one `payment:failed`. The host may send a part again within the bound and the total.
- **A cancel, and a part's expiry on an open channel,** fail the payment whole, as for any payment. A part still out may yet settle, which completes it, as before.
- **On the chain,** each part ends on its own: claimed by the peer with the preimage, which completes the payment, or taken back by this node's timeout or left out of the commitment that confirmed, which fails that part alone. Each part out on a channel that goes to the chain is an output whose timeout takes a fee coin of its own, with no deadline, as the node's own payments do; they are never refused for fee coins.
- **A part that ends without paying after the payment completed** (the peer did not claim it in time, and the chain took it back) is marked and logged `asset_part_ended_after_payment`; the record keeps its figures, since the payee was paid in full.
- The host hears of each part's end through `onHtlcResolved`, as of any asset HTLC; a part refused at its add is told by the throw.

At a restore, a part recorded and never added leaves the record, as for any asset payment; the record fails only when no other part of it is live in its channel, no preimage of it is stored and it is not unresolved.

### The spending limits

A daemon admits each part at its gate and judges the payment whole: its per-payment limit is on what the parts that have not failed and this one ask their first hops to carry, each never less than its carrier; its daily limit is on each part beside every claim held, as for any payment. Each part's claim is tied to the part and given back when the part fails or is refused at its add. At the settle, live or at the reconciliation after a stop, the day is charged what every part that did not fail asked its first hop to carry. The fee it shows for such a payment is what those parts asked over what they were worth.

### Going back to an earlier build

Nothing new is stored but the metadata keys, which every build keeps with the record. An earlier build reads the record as an asset payment and ends each part through its mapping and its monitor, so no HTLC is left unclaimed or unspent at its timeout. It knows one HTLC per payment: it turns the record FAILED at the first part that fails, with `payment:failed`, and COMPLETED again when a part settles; its pass at a restore may fail a record whose preimage is stored, which the fulfil's replay then completes; and its daemon charges the settle at one part's claim. So a node goes back only once no part is out: its host stops setting `sendInParts`, and it waits until `getAuxiliaryChannelInfo` lists no HTLC with `direction: 'offered'` on any asset channel. A drained stop waits for payments that are pending, and not for a part still out of a payment that a cancel failed or that already completed.

## A plain HTLC on an asset channel

A node offers no HTLC without units over an asset channel, but its peer may: a node with more than one channel to a peer may forward an ordinary payment over any of them, and its forwarding can pick the asset channel. Such an HTLC, a plain HTLC, carries bitcoin and no custom records. One that ends at the node, as the payment of an invoice of the node does, is put to the host as every HTLC that ends at the node is (`valueIncomingHtlc`): with no `auxiliaryAmount`, with `wireAmountMsat` the bitcoin it carries, and with `invoice` the node's own record of the hash when the hash is an invoice the node made. One that does not end at the node is refused as a forward (see "Which HTLCs the host is asked about"). No member of `AUXILIARY_CHANNELS_API` names this part: a host takes part by the value it answers.

### What the host may answer

- **A value.** The HTLC is the host's at that value, which the node goes on with in place of the bitcoin on the wire, as for any HTLC the host values. A host that takes the payment of an ordinary invoice of the node over an asset channel answers `wireAmountMsat`, and the node judges the HTLC as it judges an ordinary payment.
- **`undefined`**, "not mine", or **a throw**: the HTLC is failed back with `incorrect_or_unknown_payment_details`, as is every HTLC of an asset channel that the host does not know.

### What the node does with one the host values

Every check of an ordinary final hop applies: the amount against the onion and the invoice, the payment secret, the metadata, a set and a hold. The payment and the invoice are an ordinary payment's, with no `auxiliary` mark, and `onHtlcResolved` hears nothing of the HTLC: it hears of HTLCs with units alone. A claim of an HTLC of an asset channel on the chain is made by the node's decision to settle it, written with the channel's row, and by nothing else, so that decision is written by the time anything reveals the preimage:

- **A payment of one HTLC** is settled once the channel takes its fulfil, which writes the decision with the update.
- **A part of a set.** An ordinary invoice paid in parts collects its parts over ordinary channels and asset channels alike. Once the set is complete, nothing is written or revealed until every part on an asset channel can take its fulfil at once, by the checks each part of a set of asset parts passes (see "An asset invoice paid in parts"), and the record of the hash is the node's incoming payment, pending. Otherwise the whole set is failed back with `temporary_node_failure` (with `incorrect_or_unknown_payment_details`, each part's value and the height, when a part is too near its expiry), logged `set_on_asset_channel_not_settled` with a `reason`. The set is then committed as a set of asset parts is: the payment COMPLETED, with every part in `settledHtlcs`, and the decision to settle each part on an asset channel are written in one transition, with the rows of those channels. A write that does not land fails the set back (`reason` `write`) with nothing written or revealed. From that write on the set is committed: the preimage goes to the monitors and the fulfils are made, as for any set, and after a stop each part is fulfilled from the record on its channel's reestablish. A part of a completed payment whose fulfil its channel cannot take on a reestablish has its decision written then, by which a close claims it. At a restore, a decision to settle such a part that stands while its payment is not COMPLETED is taken back with its channel's row, logged `set_on_asset_channel_settle_taken_back`, and the part is failed back as any part of a set that does not settle. A take-back the channel refuses (its channel is closing or on the chain, or its row is not written) leaves the decision standing, and the part is settled by it: with its set, should the set complete again and settle, or else by a claim at the claim buffer, which reveals the preimage.
- **A hold.** The HTLC is parked with no mark, and settled or cancelled as on an ordinary channel (`settleHeldHtlc`, `cancelHoldInvoice`). The settle of a set with such a part first writes the decision to settle each of its parts on asset channels, all or none, in one transition: one that cannot be written stops the settle with nothing revealed (`settleHeldHtlc` answers false, logged `held_set_decisions_unwritten`), and the set stays parked, bound to its settle, which the node asks again at each block and on a reestablish. While the asset channel is on the chain, a settle is taken outside the cancel margin and written as the decision to settle the HTLC, and the hold ends with the chain: COMPLETED once the claim of the HTLC's output is 100 blocks deep, cancelled once the peer's timeout is. An HTLC under the dust limit has no output on the commitment, and its hold ends cancelled once the commitment is 100 blocks deep, whether or not a settle was taken. A cancel on the chain writes the decision to fail the HTLC and ends the hold at once. A set ends by the rule of a set of asset parts: COMPLETED with every part it settled, off the chain or claimed on it, its amount lowered by a part lost on the chain (one with no output, one the peer took back, or one taken by a penalty), and cancelled only when no part of it settled. A part claimed on the chain while another part of the set waits is kept with what the set settled, so the set's end counts it. The record, `heldAmountMsat` and `htlcCount` of `hold:settled` count the parts the set settled.
- **On the chain.** The HTLC's output carries no units, and the node resolves it as an ordinary channel's, by its decision. From the peer's commitment the node claims it with the preimage, the fee paid from the output. From its own, it spends it by the HTLC-success transaction the peer signed, whose whole fee comes from the fee coins (`fixedOutputFees`). Each funded transaction is kept, those a fee raise replaced included, so the node knows whichever of them confirms as its own. The output that transaction makes is swept once its delay has passed, as an ordinary second-level output that pays its own fee: the sweep is raised when it is not in a block, and one whose fee the output would not cover is made once the fee rate allows it. A revoked commitment of the peer that carries such an output is punished as any. An HTLC the node did not decide to settle is the peer's to take back by its timeout.

### Where its bitcoin goes

The bitcoin of a plain HTLC the node settles joins the node's side of the asset channel: the channel's `localBalanceMsat` grows by it, and so does `getBalance().auxiliaryBalanceMsat`, while the `localBalanceMsat` of `getBalance()` does not. The units on each side are as they were. Like all bitcoin on an asset channel, it is not sent over Lightning as a payment of its own: it leaves as the carriers of the node's asset HTLCs, or at a close of the channel, in what the close pays the node.

### A payment of the node's own

A plain HTLC on an asset channel whose payment hash the node is paying is failed back with `incorrect_or_unknown_payment_details`, and the host is not asked. The node is paying a hash when it holds an outgoing record of it, of any status, in memory or pruned from it, a retry context of it, or an HTLC of it that it offered on any channel. So the last leg of a rebalance, or of a circular payment of the node's own, never ends over an asset channel, as a rebalance never takes an asset channel as one of its two channels. The rule is read when the HTLC arrives: a held HTLC is valued once, and is neither asked about again nor checked again when it is gone through again (a reestablish, a restart). An HTLC with units, and a plain HTLC on an ordinary channel, are asked about as any.

### Going back to an earlier build

To go back, a host first stops valuing a plain HTLC on an asset channel, answering `undefined` for each, and the node waits until none is in flight or held: until `getAuxiliaryChannelInfo` lists no HTLC without `auxiliaryAmount` on any asset channel.

## Dual-funded asset opening on regtest

A host that implements `channel.IAuxiliaryDualFunding` can supply it as `auxiliaryChannels.dualFunding` when the engine advertises the `dualFunding:v1` surface. Each peer needs an original wallet initialized with `--dual-funded-assets`, an authenticated peer connection and a chain backend that can verify unspent inputs. The opener calls `openChannelV2(peer, { fundingSatoshis, dualFundedAssets: true })`. The acceptor's synchronous `contribution` policy chooses its Bitcoin contribution for that peer. Returning `undefined` declines before key allocation. Only private channels with positive confirmation depth are accepted.

Peers advertise private optional init bit 457 alongside channel type, dual funding, Taproot overlay and fixed asset HTLC outputs. The exact channel type contains compulsory bits 456 and 2026. It uses the joint asset root in the Bitcoin funding key and final CSV payout scripts. The asset host verifies every input history, virtual signature, output commitment, change amount, fee and allocation by issuance. Both peers must independently derive the same transaction and commitments.

The custom message envelope carries version 1 and subtype 96. Its payload begins with version 1, a one-byte phase, the 32-byte attempt ID, a 32-byte SHA-256 digest, and big-endian 32-bit total length and offset. Object phases 0 through 3 carry the proposals, authorizations, final manifest digest and exit shares respectively. Chunks use aligned 32 KiB offsets and a maximum object size of 4 MiB. Phases 4 and 5 acknowledge the layout and final digest. Phase 6 reports the completed construction digest on reconnect, or 32 zero bytes when construction must be replayed. All three digest-only frames have zero length and offset. The attempt ID is the v2 channel ID derived from the fresh revocation basepoints. Subtype 97 carries version 1, the attempt ID, the provider plan digest and the 64-byte consent signature in that order.

Each side authenticates both proposal objects and the Bitcoin layout before signing a virtual transfer. The engine enforces the agreed BOLT interactive turns, checks the final manifest and persists both exit descriptions. A wallet supplies its Bitcoin witnesses only after it has a verified, fully signed local commitment and the proofs to recover its outputs. `confirmFunding` imports the proofs at the accepted funding depth before readiness. `retractFunding` handles removal from the accepted chain. `recoverOutput` receives the exact commitment transaction, payout index, CSV delay and a signer restricted to its original output. The host persists the signed payout and imports a spendable receipt when its anchor confirms. Host signing, import, retraction, retirement and payout callbacks must support exact replay after restart.

The original device can unilaterally close from commitment zero. Applications should use this profile for opening and on-chain recovery. Asset payments and splices on this profile require further protocol support.

## Private asset splices on regtest

Initialize each original wallet with `beignet init --network regtest --asset-splice`. Configure its dual-funding provider with a local splice selection policy, open a private dual-funded asset channel and wait for both wallets to confirm the opening. The engine exposes `assetSplice:v1` for providers implementing `channel.AssetSpliceHost`. Both peers must advertise optional init bit 459, quiescence and splicing in addition to the asset opening features.

On `LightningNode`, call `await lightningNode.startAssetSplice(channelId, { fundingFeeratePerkw, minimumDepth })` with a 32-byte `Buffer`, a positive feerate and one to six confirmations. On `BeignetNode`, call `await beignetNode.startAssetSplice(channelIdHex, fundingFeeratePerkw, minimumDepth)` with the hex channel ID. The CLI command is `beignet channel asset-splice <channel-id> <feerate-per-kw> <minimum-depth>`. HTTP clients can send `X-Idempotency-Key` with `POST /channel/asset-splice`. Retrying the same key and body returns the first successful response for up to 24 hours while the daemon stays running.

Starting a splice begins quiescence. Each wallet's local policy chooses its Bitcoin contribution, asset inputs, withdrawals, change and fee budget. A Bitcoin-only splice carries the full asset inventory into the new output. This profile allows one pending splice per channel, and peers decline negotiated funding fee replacements. The node emits `splice:complete` after the accepted chain proves the transaction, both locks agree and the wallet imports the confirmed receipts.

The version 1 custom envelope uses subtype 98 for the proposal, agreement digests, virtual signatures and exit proofs, with the same bounds and chunk framing as the dual-funded opening. Subtype 99 carries the attempt ID, agreed digest and a 64-byte consent signature. Phases 7 and 8 of subtype 98 belong to an asset conversion (#2151): `conversion_terms` carries its terms, an object of at most 64 KiB, and `conversion_reply` the acceptor's answer, one frame of one to 201 bytes (`00` accepts, `01` and a reason decline). The conversion's `splice_init` and `splice_ack` carry the even TLV 65540, the terms digest followed by the target channel type, which every other splice path refuses. After them the conversion uses phases 0 and 4 of subtype 98 under its own attempt id: `layout` carries the host's proposal, an object of 1 byte to 4 MiB, and `layout_ack` the side's agreement digest. Frames under any other attempt, an asset splice's included, are routed as before. Subtype 96 refuses phases 7 and 8. Peers acknowledge the frozen interactive transaction and both final nonce promises before signing the candidate commitments. The original device retains an enforceable Bitcoin exit and the asset proof material for each funding output before releasing its funding witness.

On a freshly enrolled splice wallet, call `await lightningNode.startAssetSpliceUpdate(channelId, changes)` on `LightningNode` to propose a commitment update. An add specifies the offering side, its next HTLC ID, millisatoshis, payment hash, CLTV expiry and allocations by asset ID. An empty allocation list carries a Bitcoin-only HTLC. The receiver can fulfill an HTLC with its preimage or fail it. The original channel opener can propose a fee update. Values in satoshis and asset units use integer arithmetic.

Subtype 100 carries update intents, wallet signatures and acknowledgements. An update after funding signatures covers every live funding outpoint until both wallets lock the successor. Both holders verify the asset commitments and second-level HTLC spends for every outpoint before releasing a revocation. Reconnecting peers replay the saved signing round. The wallet's next splice uses its latest irrevocable balances and carries any remaining HTLCs forward.

With unresolved HTLCs, the splice peers end quiescence after 60 seconds or when the earliest HTLC reaches the local claim margin. An unsigned attempt releases its reservations. Once a wallet may have authorized the splice, it keeps its reservations and can replay an already released funding packet. If signing stays incomplete at the claim margin, the original device uses its chain view to select a signed unilateral exit.

### Unilateral close and original-device recovery

For a fresh regtest wallet, `beignet init --network regtest --asset-splice-recovery` enrolls the original device in generation 5. Both peers advertise optional init bit 461 in addition to the splice and asset-opening dependencies. The channel type includes compulsory bits 460, 456 and 2026. The installed dual-funding provider must implement `assetSpliceRecovery:v1`, including HTLC recovery, payout receipt export and restoration, and `retainAssetUpdatePeerViews`. The node calls that method with the peer's exact commitment on every live funding output before it signs any of them, and stores the same commitments itself. A peer can publish such a commitment before it returns its own signatures, so the wallet treats it as the peer's current state and claims its balance and HTLC outputs. Existing wallets keep the channel type they signed at opening.

During an unlocked splice the watcher checks the funding transaction, output index and current chain inclusion before choosing a local commitment. While the candidate is in the mempool, a proved parent can fund the close. Once the candidate confirms it can fund the close before the negotiated lock depth. A new header or a competing spend causes the watcher to recheck the selection. Once a close spends the candidate's output before the splice locks, the node stops asking the wallet to verify that candidate. A reorg or eviction that leaves the output unspent again resumes the check. The wallet reconstructs a peer commitment from the outpoint it actually spent and the corresponding signed state.

On receipt of a matching peer revocation, the beneficiary can claim the peer's delayed balance in addition to its own payment. The virtual revocation key is specific to the channel, funding outpoint, state, holder's revocation key and issuance. Each balance output has its own payout receipt. The wallet checks confirmed inclusion, ownership and proof ancestry before crediting units. Both balance payouts must be accounted for when the commitment gives the beneficiary two claims.

For unresolved HTLCs the watcher uses the recorded preimage or the negotiated expiry. A holder's zero-fee child requires a wallet fee input and preserves the signed input and output pair. The watcher follows the actual child output through its CSV delay. The installed wallet provider verifies virtual ownership, destination and fee policy and retains the proof files. The engine scopes its signing callbacks to the observed output and reconstructs virtual HTLC signature hashes from the allocation, tree roots, branch and timelocks.

After the channel is funded and ready, export an encrypted local recovery frame with `beignet backup asset-channel <channelId> <destPath>` or `await beignetNode.backupAssetChannelFrame(channelId, destPath)`. Use a new file for each export. Frames for the same channel carry a sequence and the previous frame's hash. A full SQLite backup and its HMAC also support repair. Save the extension's matching payout locators with either format.

On the enrolled original device, stop the daemon and run `beignet restore asset-channel <channelId> <backupFile>` with the original wallet, signer and device journal present. The engine authenticates the saved opening and the splice journal prefix against that device. Its current journal supplies later funding and exit records. Restoring the extension's payout locators lets the host observe the confirmed exit and import its verified payouts while the peer is offline. Signing authority stays on the enrolled device.

## Plain and asset channels in one regtest wallet

For a fresh regtest wallet, `beignet init --network regtest --asset-conversion` enrolls the original device in generation 6. The profiles the regtest wallets enroll are:

- generation 2 (`--final-commitment-updates`): plain final Taproot channels;
- generation 3 (`--dual-funded-assets`), 4 (`--asset-splice`) and 5 (`--asset-splice-recovery`): asset channels;
- generation 6 (`--asset-conversion`): plain final Taproot channels as generation 2 runs them and asset channels of the generation 5 recovery profile, side by side.

Each channel of a generation 6 wallet is driven, claimed and backed up by its own type, which its opening fixes. An asset channel keeps the generation 5 channel type and reports `walletGeneration` 5 to the host, and the host requirements are those of generation 5. The node refuses an opening of the generation 4 asset type. A build without generation 6 refuses the whole wallet.

Generation 6 nodes advertise optional init bit 463 (pair 462/463) once bit 461 is advertised, the node has channel type, shutdown anysegwit and dual funding, and its host carries the whole conversion surface: `assetConversionVersion` 1, a `conversionFeerateMarginPerKw` from 0 to 100,000 sat/kw, and the six members `conversionTerms`, `verifyConversionTerms`, `abandonConversion`, `proposeConversion`, `describeConversion` and `prepareConversion`. A generation 6 node whose host lacks one sets neither bit, and so opens no new plain final channel with a generation 6 peer. A node configured with asset channels clears simple close and bit 81 from its init. Between two peers that both set 463, the bit stands for the plain final type and its simple close. A generation 6 node opens and accepts a plain final channel only with 463 on both inits. That channel closes cooperatively through the final close, which reads no init features. An asset channel is negotiated as in generation 5, so a generation 6 wallet can hold one with a generation 5 peer.

Converting a channel from one type to the other is not available yet. Bit 463 is the feature such a conversion will negotiate. `AUXILIARY_CHANNELS_API.declared` names the part as `assetConversion:v1`: this build runs only the agreement on the terms and on the layout, and every attempt stops before its layout is signed, with no effect a host may rely on. Later builds add members to the conversion surface, and a host without them then loses bit 463 until it adds them. `beignet restore asset-channel` restores the asset channels of a generation 6 wallet, but not its plain channels.
